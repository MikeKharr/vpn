## Контекст

Одна машина: ReadyIDC, Таиланд, `45.91.134.19`, с 2026-10-02 — 8 ГБ ОЗУ.
Порты 80/443 и сертификаты четырёх имён держит Caddy проекта `zpq-ai`
(ADR адвента `2026-09-22-0611`); Caddy адвента — внутренний, за ним, в
общей внешней сети `edge`. Расчётно свободно ~1900 МиБ (ADR адвента
`2026-10-02-1519`; выведено, не замерено). Нормы, которые новый
репозиторий наследует как условие: секреты кладёт на сервер только
владелец скрытым вводом (образец — `deploy/put-secrets.sh` адвента);
`exec` в контейнеры прода агенту запрещён; закрытый список серверных
команд расширяется только через ADR (ADR адвента `2026-09-11-1230`).

REALITY хочет жить на 443 и выглядеть чужим TLS-сайтом; 443 занят Caddy
`zpq-ai`. Решение владельца — делить 443 по SNI.

## Решение

### 1. Вход: nginx `stream` в `zpq-ai` делит 443 по SNI; маска — свой поддомен

**В `zpq-ai` перед Caddy встаёт единица `sni` — nginx с `ssl_preread`,
единственный владелец `443` на хосте. Одно правило: SNI маски →
`vpn:443` по сети `edge`; всё остальное → Caddy `zpq-ai`, как сегодня.
Обе ветки — с PROXY protocol, чтобы ни один сайт не потерял адрес
посетителя. Маска — свежий поддомен `zpq.ai` с настоящей страницей и
сертификатом от того же Caddy. Порт 443 и сертификаты остаются у
`zpq-ai`: маршрутизатор — его единица, VPN — только upstream за одним
правилом.**

Что видит зонд. Стук на `443` с SNI маски без ключа REALITY: nginx
отдаёт соединение Xray, Xray не находит аутентификации и пробрасывает
байты в Caddy (`target`), зонд получает настоящий сертификат маски и
настоящую страницу. Стук с SNI `zpq.ai`/`challenge.`/`mail.` — мимо VPN,
прямо в Caddy, как сегодня. Стук с чужим SNI — в Caddy, ответ как на
любое незнакомое имя. Имя маски живёт на этом IP по DNS; это свойство
участники обсуждений Xray называют главным отличием живых установок от
заблокированных в марте 2026 (Discussion #5758), а «свежий поддомен на
чистом IP» — рабочим приёмом (Discussion #4035).

**Маска — заново под 443.** `zpq.ai` как `serverName` отпадает: правило
по SNI не отличает браузер от клиента VPN, весь `zpq.ai` пришлось бы
пустить через Xray, и падение VPN-контейнера роняло бы главный сайт.
Свой поддомен ограничивает зону поражения одним именем, которым никто,
кроме зонда, не пользуется. Цена: A-запись (владелец, у регистратора),
блок сайта и статическая страница в `zpq-ai`, сертификат выпускается
сам (HTTP-01 на 80 у Caddy не меняется). Имя — `cdn.zpq.ai`, выбрано
владельцем: нейтральное, объяснимое (`file_server` со статикой — ровно
то, что Caddy за ним и делает), без слов «vpn», «proxy», «tunnel».
A-запись заведена 2026-10-03. `www.zpq.ai` отклонён («Альтернативы»).

**Выбор маршрутизатора.** Кандидаты и почему nginx:

- **nginx `stream` + `ssl_preread`** — выбран. Официальный образ
  `nginx:<версия>-alpine`; в сборочных флагах пакетов nginx (`pkg-oss`,
  `alpine/Makefile` и `debian/Makefile`) есть
  `--with-stream_ssl_preread_module` и `--with-stream_realip_module`;
  `proxy_protocol on|v2`; `proxy_pass $переменная` с `resolver` — upstream
  разрешается в момент соединения, а не на старте. Конфиг — 15 строк.
  Рабочая связка с REALITY задокументирована у Xray (Issue #1697).
- **HAProxy** — равноценен (`req.ssl_sni`, `send-proxy-v2`, `resolvers`
  с `init-addr none`), официальный образ; не выбран только потому, что
  второй инструмент не даёт ничего сверх первого, а рецепт с Xray
  описан для nginx.
- **Caddy `layer4`** — отклонён: плагин, нужна сборка `xcaddy` и свой
  образ Caddy в `zpq-ai` вместо официального; ломает «образ без плагинов».
- **Xray fallback / Xray на 443** — отклонён: входом всей машины становится
  VPN-контейнер из другого репозитория; нарушает «443 у `zpq-ai`».

**Межрепозиторный контракт.** Три строки, которые оба репозитория знают
дословно. Живёт в обоих: здесь — полностью (таблица, порядок выкатки,
откат), в `zpq-ai` — ссылка на этот ADR и та же таблица; правка одной
стороны без другой — дефект PR, ловится ревью, не CI:

| Что | Значение | Владелец |
| --- | --- | --- |
| Имя маски | `cdn.zpq.ai` | `zpq-ai` (страница, сертификат); A-запись — владелец, заведена 2026-10-03 |
| Алиас VPN в сети `edge` | `vpn`, порт `443` внутри контейнера, ждёт PROXY protocol v2 | репозиторий VPN |
| Алиас Caddy `zpq-ai` в `edge` | как в compose `zpq-ai` (не читал; приватный) | `zpq-ai` |

Что меняется в `zpq-ai` (один PR):

1. Единица `sni`: образ nginx закреплён дайджестом; `ports: "443:443"`;
   `networks: [edge]`; конфиг:
   `stream { resolver 127.0.0.11 valid=30s; map $ssl_preread_server_name $up { cdn.zpq.ai vpn:443; default <caddy>:443; } server { listen 443 reuseport; ssl_preread on; proxy_protocol v2; proxy_connect_timeout 5s; proxy_pass $up; } }`.
   Переменная в `proxy_pass` обязательна: статический `upstream vpn`
   не разрешится, если VPN ещё не поднят, и nginx **не стартует** —
   тогда легли бы все сайты. С `resolver` + переменной отказ локален:
   соединения с SNI маски рвутся, остальное живёт.
2. Caddy: из `ports` уходит `"443:443"` (80 остаётся — ACME HTTP-01 и
   редиректы без изменений); в глобальные опции —
   `servers { listener_wrappers { proxy_protocol { allow <подсеть edge> } tls } }`
   (встроен в Caddy с 2.7.0; `proxy_protocol` ставится до `tls`).
   `trusted_proxies` и `header_up X-Forwarded-For {client_ip}` не
   трогаются: адрес посетителя теперь приходит из PROXY-заголовка, и
   `{client_ip}` остаётся настоящим — дни адвента с лимитерами по адресу
   ничего не замечают.
3. Блок сайта маски: `https://cdn.zpq.ai { file_server }` с одной
   статической страницей.

Что в репозитории VPN: контейнер Xray в `edge` под алиасом `vpn`, порт
не публикуется; inbound на `443` с `acceptProxyProtocol: true`; второй
inbound на `8443` без PROXY — запасной, **закрыт**: в compose строки
`ports` нет, она добавляется одним PR только при откате.

**Порядок выкатки двух репозиториев и простой.**

1. Репозиторий VPN — первым: `up -d` ставит контейнер в `edge`; снаружи
   он недостижим, никому не мешает. Простоя нет.
2. Владелец: A-запись `cdn.zpq.ai` → `45.91.134.19` — **сделано 2026-10-03**.
3. `zpq-ai`: один PR → `deploy.yml` → `docker compose up -d`. Caddy
   пересоздаётся (сменились `ports`), `sni` стартует. **Окно простоя —
   с момента остановки старого Caddy до старта `sni` и нового Caddy:
   ожидаемо 5–20 с для всех четырёх имён на 443 и для 80 на время
   пересоздания Caddy.** Почта на 465/993 (Stalwart, свои порты) не
   затрагивается. Сократить окно нечем: 443 один, второго IP нет;
   уменьшить можно только вероятность повтора — `caddy validate` и
   `nginx -t` в CI `zpq-ai` до выкатки, чтобы не пересоздавать дважды.
4. Проверки: четыре имени отвечают как до; `curl -sv --resolve
   cdn.zpq.ai:443:45.91.134.19 https://cdn.zpq.ai/` — сертификат
   маски, 200; подключение с устройства; журнал Caddy показывает адрес
   посетителя, а не адрес `sni`.

Выкатка одного без другого: `zpq-ai` без VPN — соединения с SNI маски
получают сброс, сайты живут (п. 1 выше); VPN без правки `zpq-ai` —
контейнер здоров и недостижим. Ни в одном порядке сайты не падают;
падает только VPN. Обновление VPN-контейнера (`up -d` с новым
дайджестом) сайты не трогает вовсе: `sni` держит соединения с ними сам.

**Откат на прежнюю схему Caddy:443 — минуты.** Файлы `zpq-ai` на сервере
приходят с раннера, git-клона там нет (ADR адвента `2026-09-22-0611`,
п. 5), поэтому откат — `workflow_dispatch` `deploy.yml` в `zpq-ai` с
прежним sha: **2–4 минуты** прогона плюс те же 5–20 с пересоздания
Caddy. Быстрее — только руками владельца на сервере (правка compose и
`up -d`), что проект не практикует. После отката VPN недоступен до PR в
репозитории VPN, который включает `ports: "8443:8443"` (минуты CI) —
клиенты заранее держат второй сервер «`cdn.zpq.ai:8443`» в списке
и переключаются вручную. Это и есть запасной путь: тот же Xray, тот же
`target`, та же маска, порт другой.

**Логи и реальный адрес.** `sni` — `access_log off` (единственное, что
он мог бы записать, — SNI и адрес, то есть факт обращения к VPN);
`error_log` уровня `warn`. Caddy видит адрес посетителя из PROXY и пишет
его в свой access-лог для сайтов, как сегодня; для маски — адреса зондов
(Xray без `xver` передаёт Caddy свой адрес; `xver: 2` отдал бы адрес
зонда, но требует внести `vpn` в `allow` обёртки — не нужно). Xray
получает адрес клиента через `acceptProxyProtocol` и **не пишет его
никуда** (п. 6).

### 2. Ядро: Xray-core, голый конфиг, без панели

**Официальный образ `ghcr.io/xtls/xray-core`, закреплённый дайджестом;
`config.json` — шаблон в репозитории; панели нет.**

- Xray-core — эталонная реализация REALITY и `xtls-rprx-vision`;
  изменения протокола появляются в нём первыми. Сентябрь 2026 показал
  цену лага: с v26.9.8 сервер отвергает ClientHello без key share
  `X25519MLKEM768`, и все клиенты на sing-box (1.12.25 – 1.15.0-alpha)
  перестали подключаться (SagerNet/sing-box #4520, открыт на 2026-09-26).
  Серверу на sing-box досталась бы обратная сторона того же лага.
- Панель — веб-админка на публичной машине с правом переписывать конфиг
  ядра. 3x-ui: два CVE 2025–2026 (RCE 9.8 в скрипте обновления до v2.5.3;
  запись файлов на хост через импорт БД), отчёты о майнере в контейнере.
  Marzban: последний коммит 2025-01-10, «проект мёртв?» без ответа.
  Remnawave: AGPL, NestJS + PostgreSQL + Redis, минимум 2 ГБ, нода на
  отдельном сервере. Hiddify-Manager: минимум 1 ГБ, 20+ протоколов. Всё
  это — для десятков пользователей; здесь два устройства одного человека.
- Голый конфиг даёт то, что проект уже умеет: diff в PR, `xray run -test`
  в CI, выкатка из `main`, откат — предыдущий sha.

**Версия ядра привязана к клиентам.** Клиент на Xray-core — ядро
последнее (на 2026-09-30 — v26.9.30). Клиент на sing-box — пин v26.7.28
до закрытия #4520, с ценой: в 26.9.x чинилась утечка памяти REALITY (по
тексту #4520; фикс не читал), а v26.7.28 сам ломал Vision у части
iOS-клиентов (XTLS #6728, 2026-09-06, закрыт «not planned» — тогда пин
v26.6.27).

### 3. Параметры REALITY

| Поле | Значение | Почему |
| --- | --- | --- |
| `target` | Caddy `zpq-ai` в `edge`, порт 443 | п. 1; TLS 1.3 + H2 у Caddy по умолчанию |
| `serverNames` | `cdn.zpq.ai` | SAN реального сертификата; `zpq.ai`, `mail.`, `challenge.` не трогать |
| `shortIds` | по одному 8-hex на устройство | различитель клиентов (документация); отзыв = удаление пары UUID + shortId |
| `privateKey` | `xray x25519` руками владельца | секрет; публичный ключ тоже не публикуется (им любой проходит слой REALITY до VLESS) |
| `flow` | `xtls-rprx-vision` у каждого клиента | без Vision — TLS-in-TLS по длинам пакетов |
| `fingerprint` | `chrome` | в metacubex/utls (sing-box/mihomo) гибридный key share есть только у `chrome`; у клиентов на Xray-core поведение `firefox` не проверено |
| `xver` | `0` | п. 1, «Логи» |
| `acceptProxyProtocol` | `true` на inbound 443 | за `sni` с `proxy_protocol v2` |
| порт | `443` снаружи; `8443` — запасной inbound, закрыт | п. 1 |

Что ломает маскировку на практике (по обсуждениям Xray и net4people, даты
в «Проверено лично»): SNI, не живущий на этом IP; маска из «большого
бренда» — её режут по CIDR-белым спискам целиком; `target` без TLS 1.3/H2
или с редиректом; отпечаток клиента, не совпадающий с реальным
браузером; и — с ноября 2025 на мобильных сетях РФ — сам отпечаток
`chrome`, где помогал `firefox`. Последнее сталкивается с требованием
Xray ≥ 26.9.8: отпечаток и версия ядра выбираются вместе.

### 5. Выдача конфигов: ссылки руками, подписки нет

**`vless://`-ссылка собирается скриптом в репозитории из шаблона и
значений, которые владелец вводит скрыто; передаётся на устройство
AirDrop'ом или через менеджер паролей; QR — тем же скриптом офлайн, в
терминале владельца.** Серверной страницы подписки нет. На каждое
устройство — две ссылки: `:443` (рабочая) и `:8443` (запасная, п. 1).

Подписка на публичном адресе — **секрет в URL**: путь с токеном уходит
в журналы Caddy, историю браузера, превью мессенджеров; отозвать его
можно только сменой пути, то есть переустановкой у всех устройств. Для
двух устройств выигрыш (обновление одной кнопкой) не стоит ещё одной
публичной ручки и правки в `zpq-ai`.

### 6. Эксплуатация

- **Выкатка.** Свой `deploy/compose.yml` и `deploy.yml` по образцу
  `zpq-ai` (ADR адвента `2026-09-22-0611`, п. 5): `rsync` каталога
  `deploy/` и `docker compose up -d`; в CI — `xray run -test -c` на том
  же образе с фиктивными значениями и `docker compose config`. Закрытый
  список серверных команд наследуется дословно; `exec` запрещён.
- **Секреты.** `deploy/secrets.env` (`REALITY_PRIVATE_KEY`, `UUID_<устр>`,
  `SHORTID_<устр>`) кладёт `deploy/put-secrets.sh` по форме адвента:
  `read -rs`, значение уходит на сервер по stdin через ssh, в команде и
  транскрипте не появляется. Xray не читает переменные окружения, поэтому
  `config.json` в репозитории — шаблон с плейсхолдерами; единица `render`
  на закреплённом `alpine` подставляет значения в tmpfs-том на старте
  (образец — `cron` в compose адвента: значения живут только в памяти
  контейнера). Ключи генерирует владелец на своей машине:
  `docker run --rm <образ> x25519`, `uuidgen`, `openssl rand -hex 4` —
  вывод в его терминал, не в агентскую сессию.
- **Обновление ядра** — PR со сменой дайджеста; `xray run -test` в CI
  ловит несовместимость конфига; после выкатки — одно подключение с
  каждого устройства (сентябрьский эпизод и #6728 показывают, что
  ломается именно стык версий сервер–клиент).
- **Ротация ключа** — новый `x25519` → `put-secrets.sh` → пересоздание
  контейнера → переустановка двух ссылок на обоих устройствах. UUID
  ротируются независимо от ключа.
- **Отзыв устройства** — удаление его UUID и shortId из шаблона (PR) и
  строки из `secrets.env` (владелец), пересоздание. Утечка ссылки с
  одного устройства не трогает второе.
- **Что логировать нельзя.** `log.access: "none"`, `loglevel: "warning"`,
  `dnsLog: false`; никакой статистики по адресам назначения; docker-журнал
  `json-file` `max-size 10m`, `max-file 3`; у `sni` — `access_log off`
  (п. 1). Наблюдаемость — `docker compose ps`, `restart: unless-stopped`,
  журнал ошибок без адресов; проверка живости — с клиента. Личный VPN:
  список посещённых адресов на сервере — ровно то, от чего он защищает.
- **Торренты через VPN — запрещены.** Условия ReadyIDC запрещают
  серверы BitTorrent; клиент на ноутбуке за VPN для провайдера — это
  трафик VPS. Правило эксплуатации, не техническое ограничение: в Xray
  оно не держится ничем, и это сказано здесь прямо.
- **Потолки рядом с жильцами.** `mem_limit: 256m`, `cpus: 1.0`,
  `oom_score_adj: 500` — как у `rag`/`ollama` в адвенте. Запас ~10× над
  оценкой простоя (~25 МиБ по чужому замеру 2026, не моему) при
  известной склонности Xray удерживать буферы после всплесков (Issue
  #6775). `sni`: `mem_limit: 64m`. Из ~1900 МиБ запаса — 320.
- **Сеть Docker.** VPN-контейнер — в `edge` под алиасом `vpn` и больше
  нигде; порт не публикуется (п. 1). В `edge` он видит Caddy `zpq-ai`,
  Caddy адвента и `sni` — все три и так публичны; жильцы видят `vpn:443`,
  за которым аутентификация REALITY + UUID. К сетям дней, `mcp`, `rag`,
  почты доступа нет. `network_mode: host` не используется.

### 7. Публичный репозиторий: что не попадает и что раскрывается

Решение владельца — репозиторий публичный. Тогда граница такая.

**Никогда не в репозитории:** приватный ключ REALITY; публичный ключ
(п. 3 — им проходят слой REALITY); UUID клиентов; shortId; готовые
`vless://`-ссылки; QR-изображения; `secrets.env`; отрендеренный
`config.json`.

**Чем это держится:**

- шаблон `config.template.json` с плейсхолдерами вида `__UUID_MAC__`;
  рендер — на сервере в tmpfs (п. 6), результат на диск и в git не
  попадает по построению;
- `.gitignore`: `deploy/secrets.env`, `deploy/*.env`, `*.png`, `*.svg`,
  `config.json`;
- шаг CI «Секреты не попали в репозиторий» по образцу `docs-guard.yml`
  адвента: краснеет на UUID (`[0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-…`
  вне `.example`), на `vless://`, на строке из 43 символов base64url
  после `Key` (формат `x25519`), на бинарных изображениях; к шагу — тест,
  исполняющий его тело на приманке (I-14 адвента — защита приезжает с
  держателем);
- скрипт ссылок печатает в терминал, а не в файл; QR — тоже в терминал.

**Что публичность раскрывает, честно:** схему целиком (nginx по SNI,
Xray, REALITY, Vision), порт 443 и запасной 8443, имя маски, а через
DNS — IP `45.91.134.19`, то есть «на этом адресе за этим именем сидит
REALITY». Для пассивного наблюдателя это ничего не меняет: без
публичного ключа и UUID соединение неотличимо от посещения маски. Для
активного — даёт точную цель: он знает, какое имя пробовать, и может
бить по IP целиком (блокировка IP — то, что в марте 2026 делали и без
чтения репозиториев). Публичный репозиторий **не ослабляет
криптографию и не даёт доступа**, но снимает неизвестность цели. Это
принятая владельцем цена.

## Обоснование

Вход решён владельцем; внутри него выбрано то, что держит зону поражения
минимальной: маршрутизатор в репозитории, которому принадлежит 443;
правило, не зависящее от существования VPN в момент старта; маска, за
которой нет ничего, кроме зонда; PROXY protocol, чтобы сайты не потеряли
адрес. Голый конфиг вместо панели — потому что панель на этой машине
защищает только себя, а конфиг на два устройства меняется раз в месяцы.
Клиент — Happ по решению владельца: единственный открытый клиент на
Xray-core (OneXray) молод и держится одним человеком с открытыми
регрессиями на Mac, а Happ зрел по оценкам и признан README Xray-core;
цена — закрытый код, и она принята.

## Последствия

Положительные:

- VPN на 443 за настоящим именем на настоящем IP; зонд на любом SNI
  видит сайт с сертификатом.
- Сайты не зависят от VPN ни в одном порядке выкатки; обновление VPN не
  трогает `sni` и Caddy.
- Адрес посетителя у сайтов сохранён; у `sni` и Xray журналов адресов нет.
- Отзыв устройства и ротация — PR плюс одна команда владельца.

Отрицательные — и честные:

- **Новый процесс перед всеми сайтами.** `sni` — единая точка отказа для
  HTTPS всей машины; его падение кладёт четыре имени. nginx стабилен, но
  это второй прокси подряд, и живой проверки двух прокси подряд перед
  днями адвента ещё не было.
- **Простой при переключении и при каждом откате:** 5–20 с на 443 и 80;
  откат — 2–4 минуты через `workflow_dispatch`, потому что git-клона на
  сервере нет.
- **PROXY protocol становится обязательным** для всех HTTPS-соединений
  машины; ошибка в `allow` или в порядке обёрток — все сайты видят адрес
  `sni` вместо посетителя, лимитеры дней считают весь мир одним
  адресом. Проверка п. 4 порядка выкатки обязательна, держателя в CI
  нет — только живой `curl`.
- **PR в чужом репозитории.** Контракт из трёх строк живёт в двух
  местах; расхождение (переименовали алиас, сменили маску) — тихая
  поломка VPN без красного прогона.
- **VPN живёт, пока жив Caddy `zpq-ai`:** REALITY берёт сертификат из
  живого рукопожатия с `target`.
- **Два устройства — руками**, по две ссылки на каждое.
- **Закрытый клиент.** Что делает Happ с трафиком и ключами на
  устройстве, проверить нельзя; обновление клиента может сломать стык с
  ядром (ML-KEM-эпизод), и чинить это нечем, кроме ожидания или смены
  клиента. Открытая замена — OneXray — молода (п. 4, «Альтернативы»).
- **Отпечаток `chrome` фактически обязателен** при последнем ядре (для
  клиентов на sing-box — точно; для Xray-core — не проверено), а именно
  его в 2026 режут на некоторых мобильных сетях.
- **Память — оценка, не замер**; ядра и свободная память после апгрейда
  не замерены — `nproc`, `free -m` за владельцем.
- **Публичный репозиторий называет цель** (п. 7).

## Ручные шаги и проверки

Не переезд: переносимого нет. Шаги владельца по порядку — то, что
физически требует его рук; всё остальное делает агент PR'ами.

1. Создать публичный репозиторий VPN на GitHub (агент репозиториев не
   создаёт). Принять этот ADR там; принять ADR `zpq-ai` о единице `sni`.
2. На хосте один раз: `nproc` и `free -m` — число ядер и свободная память
   после апгрейда (сейчас — оценки).
3. Пара ключей выкатки для нового репозитория: секреты `SSH_KEY`,
   `SSH_HOST`, `SSH_USER` в его environment `production`; публичный ключ
   — в `authorized_keys` пользователя `advent` на сервере (новый секрет
   на сервере — только руками владельца, как у `zpq-ai`).
4. На своей машине, в своём терминале: `docker run --rm <образ xray>
   x25519` (приватный и публичный ключ), `uuidgen` дважды, `openssl rand
   -hex 4` дважды; сохранить в менеджере паролей. Ничего из этого не
   вставлять в чат и в команды агенту.
5. `bash deploy/put-secrets.sh` из репозитория VPN — скрытый ввод пяти
   значений, файл `deploy/secrets.env` на сервере, `chmod 600`.
6. A-запись `cdn.zpq.ai` → `45.91.134.19`, TTL 300 — **выполнено
   2026-10-03**; проверено `dig @1.1.1.1 cdn.zpq.ai A` в тот же день
   (раздел «Проверено лично»).
7. Мерж PR репозитория VPN (контейнер в `edge`, снаружи недостижим), затем
   мерж PR `zpq-ai` с единицей `sni` — окно простоя 5–20 с; проверки из
   п. 1 порядка выкатки, п. 4. Мерж при консенсусе гейтов делает агент;
   момент — выбирает владелец (простой касается всех четырёх имён).
8. Установить Happ по идентификатору `id6504287215` на iPhone и Mac
   (ссылки `https://apps.apple.com/th/app/happ-proxy-utility/id6504287215`).
9. Сгенерировать две ссылки на устройство скриптом репозитория (в своём
   терминале), импортировать `:443`; `:8443` — в список, выключенной.
   Задать правила `direct` для своих имён (п. 4). Подключиться с обоих
   устройств; открыть `https://cdn.zpq.ai/` без VPN — страница с
   сертификатом.
10. Правило эксплуатации, которое держится только владельцем: торренты
    через VPN не запускать (п. 6).

## Альтернативы рассмотрены

- **Отдельный порт 8443 с маской `zpq.ai` без правок `zpq-ai`.**
  Отклонён владельцем: порт — метка в сетях, где открыты только 80/443.
  Оставлен закрытым запасным inbound для отката.
- **8443 опубликован с первого дня.** Отклонён владельцем: откат без PR
  не стоит постоянной метки на IP.
- **`www.zpq.ai` как маска.** Отклонён: редирект на апекс (документация
  REALITY советует домены без редиректа) и падение VPN ломало бы `www`;
  свежий поддомен стоит одной A-записи.
- **OneXray как клиент** (GPL-3.0, Xray-core, iPhone + Mac в TH).
  Отклонён владельцем как основной, оставлен запасным открытым
  вариантом: проект одного автора с мая 2025, 639 звёзд, 15 релизов с

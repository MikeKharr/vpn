# [2026-10-05 22:23] Второй сервер VPN на Triplify (Bangkok): независимая машина, маска `cdn2.zpq.ai`, клиент с автопереключением

Файл: `agent_docs/adr/2026-10-05-2223-second-server-triplify-failover.md`

## Статус

дословно): «Я хочу чтобы при любой ситуации трафик шел через тайланд, даже

На момент предложения: на сервер 2 не ходили; ssh на `160.236.128.28:22`
снаружи **не отвечает** (таймаут) — причина неизвестна (шаг 0 «Ручных

## Решение

**Сервер 2 — отдельная машина у другого провайдера в другой автономной
системе, с тем же шаблоном Xray и собственной маской `cdn2.zpq.ai` за своим
Caddy. Выкатка — тот же `deploy.yml`, матрица из двух хостов, отказ одного не
останавливает другого. Ключ REALITY — свой у каждого сервера; UUID и shortId
устройств — общие. Клиент — Happ с полным JSON Xray: балансер «основной →
резервный» (`selector: th1`, `fallbackTag: th2`) под observatory; два
обычных профиля остаются полом, который работает без проверок. Падение
сервера владельцу сообщает cron-workflow этого репозитория письмом GitHub.**

Имена хостов в репозитории: `th1` — ReadyIDC (`45.91.134.23`, маска
`cdn.zpq.ai`), `th2` — Triplify (`160.236.128.28`, маска `cdn2.zpq.ai`).

### 1. Сервер 2: что ставит владелец, чего агент не делает никогда

Машина поднимается скриптом `deploy/bootstrap.sh` этого репозитория (новый
файл, образец — `deploy/bootstrap.sh` адвента, без клона и без сети `edge`):
пользователь выкатки с именем, которое выбирает владелец (не `advent`, не
`root`, не `ubuntu` — имя уедет в секрет `SSH_USER` и в репозитории не
появится); `authorized_keys` — ключ владельца и публичная половина ключа
выкатки; sshd — только ключи, `PermitRootLogin no`; `ufw` — `deny incoming`,
`allow 22,80,443/tcp`; fail2ban на sshd; `unattended-upgrades`; Docker CE из
репозитория Docker; каталог `~/vpn/deploy`. Запускает **владелец** от root
один раз, файлом (`scp` + `ssh root@… 'bash /tmp/bootstrap.sh'` — не через
stdin, урок адвента 2026-09-07).

Агент **никогда**: не входит на сервер 2 (граница 3 `AGENTS.md`
распространяется на оба хоста); не генерирует и не видит ключ REALITY, UUID,
shortId, ключ выкатки; не меняет сеть хоста, `ufw`, sshd; не создаёт учётных
записей; не кладёт `secrets.env`. Единственный путь агента на сервер 2 —
`deploy.yml` по push в `main`.

Порт 80 на сервере 2 открыт **намеренно**: по нему Caddy маски выпускает
сертификат (HTTP-01) и отвечает редиректом, как любой хост статики. Порты
Docker идут мимо `ufw` (факт ADR `zpq-ai` `2026-09-24-0855`), поэтому `ufw`
здесь — защита sshd и всего, что не Docker; что наружу публикует Docker,
держит шаг CI (п. 2).

### 2. Выкатка: одна матрица, два хоста, раздельные секреты

- `deploy.yml`: `strategy.matrix.include` из двух строк `{host: th1,
  environment: production}` и `{host: th2, environment: production-th2}`;
  `fail-fast: false` — красный th2 не отменяет th1 и наоборот;
  `max-parallel: 1`, th1 первым — чтобы два сервера не пересоздавались
  одновременно (окно «оба лежат» — только одно, названо в «Последствиях»).
  `environment: ${{ matrix.environment }}`; секреты `SSH_KEY`, `SSH_HOST`,
  `SSH_USER`, `SSH_PORT` — в каждом environment свои. Существующий
  `production` не переименовывается: владельцу не пришлось бы вводить три
  значения заново.
- Compose — общий файл плюс наложение на хост: `deploy/compose.yml` (render,
  xray — без `ports`, без сетей, без `XRAY_TARGET`/`MASK_NAME`),
  `deploy/hosts/th1/compose.yml` (сеть `edge`, алиас `vpn`,
  `45.91.134.23:443:8443`, `XRAY_TARGET=zpq:8444`, `MASK_NAME=cdn.zpq.ai`),
  `deploy/hosts/th2/compose.yml` (служба `mask` — Caddy по digest,
  `160.236.128.28:80:80`, внутренняя сеть `mask`; у xray
  `160.236.128.28:443:8443`, `XRAY_TARGET=mask:8444`,
  `MASK_NAME=cdn2.zpq.ai`). На сервере: `docker compose -f compose.yml -f
  hosts/$HOST/compose.yml`. Ключ хоста — `deploy/hosts/<host>/host-key.pub`.
  Шаблон `config.template.json` получает один новый плейсхолдер
  `__MASK_NAME__` вместо литерала `cdn.zpq.ai` в `serverNames`; `render.sh`
  проверяет его форму как имя хоста.
- Держатели CI переписываются по хостам: «ровно один порт» становится «у
  th1 ровно один — `45.91.134.23:443:8443`; у th2 ровно два —
  `160.236.128.28:443:8443` у xray и `160.236.128.28:80:80` у mask»; алиас
  `vpn` и `XRAY_TARGET=zpq:8444` сверяются только у th1; `xray run -test`
  гоняется на обоих наложениях. Шаг выкатки «Снаружи отвечает маска» берёт
  имя и адрес из наложения своего хоста.
- `rsync` везёт весь `deploy/` на оба хоста — наложение чужого хоста лежит
  рядом мёртвым файлом; это дешевле, чем разные наборы файлов на двух
  машинах.

### 3. Личность клиента: ключ REALITY — на сервер, UUID и shortId — на устройство

Приватный ключ REALITY — у каждого сервера свой (`x25519` дважды).
Компрометация одного хоста (у th2 провайдер трёхмесячной давности в BGP —
«Проверено лично») не даёт выдавать себя за другой; клиентской ссылке это не
стоит ничего — она и так различается адресом. UUID и shortId устройства —
одни и те же на обоих серверах: это личность **устройства**, и утечка ссылки
с устройства раскрывает оба сервера независимо от того, совпадают ли там
значения; отзыв устройства — одна правка на обоих хостах (`put-secrets.sh`
дважды). Цена: `secrets.env` на двух машинах, ротация — два ввода.
`put-secrets.sh` теряет умолчание `SERVER=advent@challenge.zpq.ai` и требует
`SERVER=` явно — чтобы ключ th2 не уехал на th1 молча.

### 4. Клиент: JSON с балансером «основной → резервный»; два профиля — пол

Happ передаёт полный JSON Xray ядру «exactly as is», и в этом режиме «standard
HAPP routing rules and interface settings are not applied» (документация
Happ, «Проверено лично»). Форма JSON — решение; точные строки — исполняющий
PR (`bin/make-happ-json.sh`, печать в терминал, как `make-link.sh`):

- `outbounds`: `th1` и `th2` — VLESS + REALITY + Vision, **адрес —
  IP-литерал**, `serverName` — имя маски, свой `publicKey`; `direct`
  (freedom); `block` (blackhole).
- `routing.rules`: `domain:zpq.ai` → `direct`; приватные диапазоны →
  `direct` (то, что сегодня делает профиль Happ «zpq direct», — в режиме JSON
  его нет); всё остальное → `balancerTag: vpn`.
- `routing.balancers`: `{tag: vpn, selector: ["th1"], fallbackTag: "th2",
  strategy: {type: "leastPing"}}`. Селектор ловит **только** th1; пока
  observatory видит его живым — весь трафик через th1; когда «all outbounds
  cannot be connected based on observation results» — `fallbackTag`, то есть
  th2. Когда мёртвы оба — трафик идёт в th2 и не проходит: **ни при каком
  исходе он не уходит в `direct`** — это и есть «при любой ситуации через
  Таиланд» в его честной форме «через Таиланд или никуда».
- `observatory`: `subjectSelector: ["th"]`, `probeUrl`
  `https://www.gstatic.com/generate_204`, `probeInterval: "30s"`,
  `enableConcurrency: true`. Обнаружение падения — до 30 с плюс таймаут
  зонда; в это окно новые соединения висят на th1, но не утекают.

Почему основной th1, а не `leastPing` по обоим: сайты видят исходящий адрес
сервера, и при равноправном балансе он прыгал бы между `45.91.134.19` и
`160.236.128.28` — двумя AS — на каждом переключении: повторные входы,
капчи, антифрод банков. Th1 — проверенный сервер с 8 ГБ; th2 — резерв.

**Пол, который не зависит от проверок:** `bin/make-link.sh <устройство>
<хост>` печатает ссылки для th2 (имя `cdn2.zpq.ai`, запасная — IP), владелец
импортирует их вторым профилем Happ и переключается руками. Это делается в
любом случае и первым; JSON — поверх, после живой пробы на Mac (шаг 7).

### 5. DNS

`cdn2.zpq.ai A 160.236.128.28`, TTL 5 мин — **сделано владельцем** до этого
ADR. Имя даёт свойство «SNI родной для IP» (ADR `0353`, п. 1) и сертификат
маски. Клиентский JSON от зоны `zpq.ai` **не зависит** (адреса —
IP-литералы): отказ DNS или регистратора не кладёт оба сервера разом. Ссылки
пола заданы именем — у них эта зависимость есть, как сегодня.

### 6. Что скажет владельцу, что сервер умер

Балансер **прячет** падение: трафик уходит на th2, и ничего не меняется на
экране — а второе падение после скрытого первого и есть тот случай, который
владелец считает маловероятным. Поэтому — `.github/workflows/watch.yml`:
`schedule: */15 * * * *` плюс `workflow_dispatch` с полем `drill_ip` для
учебной тревоги; шаг — тот же `curl --resolve <маска>:443:<адрес> https://<маска>/` без
`-k` → 200 по каждому хосту из наложений; отказ любого — красный
прогон → письмо GitHub владельцу (уведомления о провалах cron-workflow
приходят «the user who last modified the cron syntax»). Что это
различает: «слушатель Xray жив и пробрасывает в маску» от «не отвечает»;
рукопожатие REALITY — нет. Цена и границы — «Последствия».

## Обоснование

Второй **адрес** на той же машине (ADR `1546`) не защищал от падения
машины, провайдера и блокировки `/24`; второй **провайдер** в другой AS и
другом префиксе — защищает ровно от этого класса, ничего не меняя в th1.
Своя маска на сервере 2 — потому что без неё пришлось бы либо занимать
чужой SNI (главный признак блокировок 2026), либо цеплять th2 к th1 как к
`target` (резерв, зависящий от основного). Один `deploy.yml` с матрицей —
потому что второй workflow удвоил бы каждую правку выкатки, а `fail-fast:
false` даёт независимость отказов без удвоения. Балансер с селектором на
одном outbound и `fallbackTag` — единственная форма «основной → резервный»,
которую Xray даёт без изменения адреса на каждом переключении. Cron-watch
— потому что автопереключение по построению скрывает первое падение.

  репозиторий остаётся публичным.
- `MikeKharr/zpq-ai` на диске (`19dbe05`): блок `cdn.zpq.ai:8444`
  (`log_skip`, заголовки, `X-Robots-Tag`), `http://cdn.zpq.ai` редирект,
  `servers :8444 { strict_sni_host on }`, шаг CI «Страница маски ничего не
  выдаёт» (список слов, метка `build-id`), `cdn/robots.txt`; `cdn2` в
  репозитории не упоминается.
- Документация Xray (`xtls.github.io/en/config/routing`, `observatory`):
  `fallbackTag` — «If all outbounds cannot be connected based on observation
  results, the outbound specified by this configuration item is used»;
  `leastPing` требует observatory; `observatory.probeInterval`,
  `enableConcurrency`; `selector` — префиксное совпадение.
- Документация Happ (`happ.su/main/dev-docs/examples-of-links-and-parameters`,
  раздел 3): «When the XRAY core is launched, this JSON configuration is
  passed exactly as is… standard HAPP routing rules and interface settings
  are not applied». Слов `observatory`, `balancer`, `fallback` в документации
  нет; версия ядра не названа.
- GitHub Docs, `schedule`: отключение через 60 дней без активности в публичном
  репозитории; задержки в часы пик; минимум 5 минут; уведомления —
  последнему редактору строки cron. `max-parallel` — документирован.
- Triplify: сайт — Tier III Bangkok, «Anti-DDoS, WAF, Hardware Firewall,
  Daily Backup»; ToS (тайский, читал через перевод): запрет открытых прокси/
  релеев, «Proxy, VPN or anonymity services to third parties» — только с
  письменного согласия; бэкап — обязанность клиента, кроме явно оплаченной
  услуги; приостановка без уведомления и возврата при нарушении.
- Xray-core: последний релиз v26.9.30 (2026-09-30) — тот же, что в compose;
  перекоса версий между серверами нет по построению (один digest на оба).

Неподтверждённым остаётся всё, что собрано по документации поставщика или не
прогонялось:

- что `environment: ${{ matrix.environment }}` подставляется из матрицы —
  по практике, не прогоном; при отказе — два job'а вместо матрицы;
- что `fallbackTag` срабатывает живьём и за какое время при `probeInterval
  30s` — прогона нет; что ядро в сборке Happ (iOS и Mac) несёт `observatory`
  и `balancers` — документация молчит, проверка — один импорт (шаг 7);
- кто создаёт TUN-inbound в режиме JSON Happ и нужен ли `dns`-блок для
  доменных правил — выяснится той же пробой;
- почему `160.236.128.28:22` не отвечает: VM не запущена, файрвол
  провайдера, порт закрыт — различитель в шаге 0;
- характеристики и цена NANO — со слов владельца; 2FA панели, формат
  бэкапа, выдача IPv6 — не смотрел (панель — у владельца);
- что Caddy с `protocols h1 h2` перестаёт слать `alt-svc` — по документации
  глобальных опций;
- расход минут: репозиторий публичный — минуты Actions бесплатны; при
  переводе в приватный cron в 15 минут съедал бы ~1 400 из 2 000.

## Последствия

Положительные:

- Падение машины, провайдера, префикса `/24` или блокировка одного адреса
  больше не кладут VPN; th1 не меняется ни на строку, его откат остаётся.
- Переключение автоматическое и в одну сторону: пока жив th1 — трафик с
  прежнего адреса, как решил владелец (ADR `1546`, «Решения владельцу», п. 3).
- Один шаблон, один digest, одна выкатка на оба сервера.

Отрицательные — и честные:

- **Это не два независимых сервера, а один репозиторий, один аккаунт GitHub
  и один ноутбук.** Компрометация любого из трёх даёт оба сервера; ошибка в
  `deploy.yml` или в шаблоне едет на оба (с интервалом `max-parallel: 1`, но
  едет). Подъём digest Xray, несовместимый с клиентом (эпизод ML-KEM, ADR
  `0353`), ломает **оба** одним PR — в этом окне «второй остался» неверно.
  Держатель один: живая проверка владельца после выкатки, как сегодня.
- **Два `secrets.env` и две копии UUID/shortId**; оба лежат на дисках у
  провайдеров и уезжают в их бэкапы (ReadyIDC — ежедневный образ по ADR
  адвента `1800`; Triplify — «Daily Backup» на сайте). Утечка бэкапа th2
  раскрывает UUID обоих устройств для обоих серверов — ротация UUID на двух
  хостах и переимпорт на двух устройствах. Альтернатива без ключа на диске
  (ввод при каждой загрузке) отклонена: после перезагрузки VPN лежал бы до
  рук владельца.
- **Молодой провайдер.** Префикс в BGP с июля 2026, ToS разрешают VPN
  «третьим лицам» только письменно, личное использование не названо;
  приостановка — без уведомления и возврата. Письменное подтверждение, как
  у ReadyIDC, — вопрос владельцу (п. 6 ниже).
- **Разъезд хостов.** Наложения различаются (сеть `edge` против своей маски),
  две ОС патчатся порознь, две версии Docker; что одинаково на обоих —
  держит только общий файл и ревью.
- **Режим JSON отключает интерфейс Happ**: правила «zpq direct», Tunnel DNS
  в UI перестают действовать и живут в JSON; любая правка — переимпорт на
  обоих устройствах; наблюдать, какой сервер выбран, — только `lsof` на Mac,
  на iPhone — никак. Если Happ на iOS балансер не поддерживает — остаётся пол
  с ручным переключением, то есть «второй остался» выполняется, «сам
  переключился» — нет.
- **Observatory — постоянный фоновый трафик** зондов с устройства через оба
  сервера раз в 30 с; на iPhone это батарея и трафик, величина не измерена.
- **Cron-watch — дыры**: 15 минут между зондами, задержки GitHub в часы пик,
  самоотключение через 60 дней без коммитов (репозиторий живёт, пока в него
  пишут), письмо уходит последнему редактору cron, а не «владельцу»; зонд
  видит маску, не рукопожатие. Это сторож «сервер мёртв», не «VPN работает».
- **Исходящий адрес резерва — `160.236.128.28`**: при переключении все сайты
  видят новый адрес из новой AS, сессии рвутся.
- **Порт 80 и имя `cdn2` открыты миру**; `nmap` покажет 22/80/443 — обычный
  хост статики, но хост.
- **1 ГБ ОЗУ** — Xray 256 МиБ + Caddy 64 + render 16 при незамеренной
  нагрузке; OOM на NANO ронял бы маску или ядро.
- **Третий ADR подряд о топологии за четыре дня**: контракт с `zpq-ai`,
  второй адрес, теперь второй сервер — часть текста ADR `1546`
  («единственный резерв — чужой узел») устаревает; строка статуса туда.

## Решения владельцу

Рекомендуемый вариант — первый.

1. **Принять ADR** / отклонить / принять с правками.
2. **Основной сервер:** (а) th1, th2 — резерв; (б) `leastPing` по обоим —
   цена: адрес прыгает между AS; (в) th2 основной — непроверенный провайдер
   в роли основного.
3. **Личность:** (а) свой ключ REALITY на сервер, UUID/shortId общие; (б) всё
   общее, включая ключ — компрометация одного хоста = оба; (в) всё раздельно
   — четыре UUID, выигрыша нет: ссылка живёт на устройстве.
4. **Сторож:** (а) cron-workflow в репозитории; (б) внешний монитор
   (UptimeRobot) — третья сторона регулярно стучит в маску с известных
   адресов; (в) никакого — первое падение не увидеть.
5. **Клиент:** (а) пол из двух профилей сразу, JSON после пробы на Mac;
   (б) только пол — «сам переключился» не выполняется.
6. **Triplify и VPN:** (а) спросить поддержку письменно, как у ReadyIDC
   («personal VPN server»), до выкатки; (б) принять риск приостановки без
   возврата ฿1 599.
7. **Имя пользователя выкатки на th2** — выбор владельца; агент его не
   узнает (секрет `SSH_USER`).
8. **Что показывает панель по `:22`** (шаг 0) — без ответа шаги 2–6 не
   начинаются.

## Альтернативы рассмотрены

- **Коммерческий VPN как резерв** — отклонён владельцем: выход может
  сменить страну без его ведома.
- **Чужой сайт как `target` на th2** (REALITY «взаймы») — SNI не родной
  для IP, главный признак блокировок 2026; имя `cdn2` осталось бы без дела.
- **`target` th2 → th1** (`45.91.134.19:443` через `sni`) — резерв, живущий,
  пока жив основной; сертификат `cdn`, а не `cdn2`.
- **Второй workflow для th2** — каждая правка выкатки дважды; независимость
  отказов даёт `fail-fast: false`.
- **Один environment на оба хоста** (секреты с суффиксами) — ломает текущий
  `production`, владелец вводит значения заново; выигрыша нет.
- **Два compose-файла целиком** вместо наложений — дублирование render/xray
  построчно, разъезд неизбежен.
- **Разные версии Xray на хостах** («пин на резерве») — два шаблона, два
  `-test`; перекос версий — иной риск, не меньший.
- **Один ключ REALITY на оба** / **раздельные UUID** — п. 3 «Решений
  владельцу».
- **`fallbackTag: direct`** — трафик без VPN при падении обоих; нарушает
  требование владельца буквально.
- **Поимённые записи ИИ-ботов в robots.txt**, мета `noai` — примета без
  пользы (таблица).
- **Нестандартный порт sshd** — обскурность; ключи и fail2ban дают то же.
- **Внешний монитор** — п. 4 «Решений владельцу».
- **Третий сервер / anycast / общий IP** — вне денег и смысла для двух
  устройств.

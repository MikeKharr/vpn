# [2026-10-06 10:54] Разовый запуск `bootstrap.sh` на th2 агентом; пользователь выкатки `ops`; пара REALITY th2 — окончательная

Файл: `agent_docs/adr/2026-10-06-1054-agent-runs-th2-bootstrap-once.md`

## Статус

**Принято владельцем 2026-10-06.** Дополнение к ADR
[2026-10-05-2223](2026-10-05-2223-second-server-triplify-failover.md): меняет
в нём три вещи и больше ничего. Решение целиком, топология, маска, клиент,
матрица выкатки и раздел «Индексация, блокировка, взлом, SEO» остаются как
там.

Ответ владельца дословно. Вопрос: «Кто запускает скрипт настройки (bootstrap)
на сервере Triplify?» → «Разово разрешаю агенту». Выбранный вариант, дословно:
«Дополнение к ADR: агент один раз запускает проверенный гейтами bootstrap.sh
под ssh triplify, с проверкой нового входа до закрытия root; при сбое — ваша
консоль. Дальше правило „не входить“ снова в силе».

Имя пользователя выкатки — выбор владельца по ADR `2026-10-05-2223`,
«Решения владельцу», п. 7; выбрано (2026-10-06): **`ops`**.

## Решение

### 1. Разовый вход агента на th2 — только `bootstrap.sh`, только двумя командами

Граница 3 `AGENTS.md` («на сервер агент не ходит руками») получает одно
названное исключение, ограниченное предметом и числом запусков: первичная
настройка th2 скриптом `deploy/bootstrap.sh`, прошедшим гейты в PR A-1.
Форма запуска — ровно эта:

```sh
ssh triplify 'bash -s -- ops' < deploy/bootstrap.sh
ssh -i ~/.ssh/triplify_admin ops@160.236.128.28 true   # проверка с Mac
ssh triplify 'bash -s -- ops --disable-root-login' < deploy/bootstrap.sh
```

`Host triplify` в `~/.ssh/config` владельца — `root@160.236.128.28` с ключом
`~/.ssh/triplify_admin`.

Три свойства этого исключения, и каждое — часть решения, а не обещание:

- **Запрет входа для root — ОТДЕЛЬНАЯ, вторая команда**, и между ними стоит
  проверка нового входа **с Mac**, а не из той же сессии. Скрипт сам root не
  закрывает ни при каком исходе первой фазы. Причина простая: единственная
  ошибка в `authorized_keys` при закрытии в один проход оставляет машину без
  входа вовсе, и путь назад — только консоль провайдера, то есть руки
  владельца. Держит это форма скрипта (`MODE=root-off` только по второму
  аргументу) и его отказ закрывать root при пустом `authorized_keys`
  пользователя выкатки.
- **Неинтерактивность и идемпотентность — требование, а не удобство.** Агент
  не может ответить на conffile-вопрос apt, а повторный запуск обязан быть
  безопасным: при обрыве ssh посередине единственное лекарство — запустить
  заново.
- **Правило «не входить» возвращается в силу** сразу после `--disable-root-login`
  и проверки. Дальше на th2 ходит только `deploy.yml` по push в `main`.
  Никаких «раз уж есть доступ» — ни `docker compose`, ни чтения `secrets.env`,
  ни правок на месте.

Почему запуск **со stdin**, а не `scp` + файлом, как велел ADR
`2026-10-05-2223`, п. 1: у агента нет и не должно быть права оставлять файлы
на сервере, а форма со stdin не оставляет ничего. Классический отказ такой
формы — apt на conffile-вопросе читает stdin и съедает остаток скрипта (урок
адвента 2026-09-07) — закрыт **формой файла**: всё тело завёрнуто в группу
`{ … } </dev/null`, и bash дочитывает составную команду до закрывающей
скобки прежде, чем исполнить внутри хоть одну команду. Это проверяемое
свойство, а не довод: `test/bootstrap.test.sh` кормит скрипт конвейером и
краснеет на снятии группы.

### 2. Имя пользователя выкатки — `ops`, и его необнаружимости больше нет

ADR `2026-10-05-2223` ставил имени задачу «не угадывается с первой попытки» и
обещал, что в репозитории его не будет (секрет `SSH_USER`). С этим ADR обещание
перестаёт быть правдой, и это сказано прямо: имя `ops` стоит в командах выше,
то есть в публичном репозитории и в описании PR. Цена названа, а не замазана:
обскурность имени учётной записи даёт мало, и держат sshd **ключи-only,
`PermitRootLogin no`, fail2ban и `ufw`**, а не неизвестность имени. Умолчания
в самом скрипте по-прежнему нет: имя — обязательный аргумент, потому что на
следующей машине оно может быть другим, и молчаливое умолчание выбрало бы его
за того, кто запускает.

Секрет `SSH_USER` в environment `production-th2` остаётся: он нужен выкатке,
и заводит его владелец (ADR `2026-10-05-2223`, «Ручные шаги», п. 4).

### 3. Пара REALITY для th2 уже существует и новой не будет

ADR `2026-10-05-2223`, «Ручные шаги», п. 5 требовал сгенерировать для th2
**новую** пару `x25519`. Это требование **отменяется**: владелец уже
сгенерировал пару (`xray x25519`) и уже импортировал **окончательный** профиль
Happ на оба устройства.

Что зафиксировано и чего менять нельзя:

| Что | Значение |
| --- | --- |
| приватная половина | `~/.config/vpn/th2-reality.key` на Mac владельца |
| публичная половина | `~/.config/vpn/th2-reality.pub`; уже в профиле Happ |
| адрес outbound | `160.236.128.28:443` |
| `sni` / `serverName` | `cdn2.zpq.ai` |
| UUID и shortId устройств | **ТЕ ЖЕ**, что на th1 (ADR `2026-10-05-2223`, п. 3) |
| `fp` | `chrome` |
| `flow` | `xtls-rprx-vision` |

Поэтому th2 **обязан** быть выкачен ровно с этой приватной половиной. Она
уезжает на сервер единственным путём — `SERVER=ops@160.236.128.28 bash
deploy/put-secrets.sh`, скрытым вводом из этого файла, руками владельца
(граница 2 `AGENTS.md`). Ни `bootstrap.sh`, ни выкатка ключа не генерируют и
не касаются его вовсе.

Почему переимпорт — не выход: принести конфиг на устройство из России при
лежащем VPN и есть то положение, которого вторая машина должна избегать.
Новая пара на сервере сделала бы импортированный профиль мёртвым, и починка
требовала бы ровно того, что невозможно. Ротация остаётся возможной как
осознанное действие с переимпортом на обоих устройствах, но не как попутное
следствие выкатки.

## Обоснование

Запуск руками владельца (как велел ADR `2026-10-05-2223`) означал ожидание
его рук на шаге, который ничего не решает: `bootstrap.sh` прошёл гейты, он
идемпотентен, он не касается ни одного секрета и не поднимает контейнеров.
Владелец это и сказал словами «Разово разрешаю агенту». Что осталось за
владельцем — не изменилось: новые секреты (`put-secrets.sh`, секреты
environment), принятие ADR, откат прода и консоль провайдера при сбое.

Разделение на две фазы — не процедурная вежливость, а единственная защита от
класса «машина без входа»: ни одна проверка внутри сессии root не различает
«новый вход работает» от «новый вход выглядит настроенным».

## Проверено лично (2026-10-06)

Со стороны владельца, до этого ADR:

- вход `ssh triplify` работает; `Host triplify` = `root@160.236.128.28`, ключ
  `~/.ssh/triplify_admin`; ключ хоста ED25519
  `SHA256:ebDvBDpkvV0LK3sjhbeVRMZgqkH0NFYRQ1SHCfY92cY`;
- ОС — Ubuntu 24.04.5, **перезагрузка отложена** (`reboot-required`);
- `/etc/ssh/sshd_config.d/00-hardening.conf` уже лежит:
  `PasswordAuthentication no`, `KbdInteractiveAuthentication no`,
  `PermitRootLogin prohibit-password`. Лексический порядок каталога делает
  этот файл сильнее нашего `99-…`, поэтому `bootstrap.sh` сверяет
  **действующее** значение (`sshd -T`), а не записанное, и в фазе 2 глушит
  чужие строки `PermitRootLogin` с сохранением копии;
- `ufw` активен, 22/tcp разрешён;
- профиль Happ для th2 импортирован окончательно, пара `x25519` лежит в
  `~/.config/vpn/`.

Со стороны агента, в этом PR:

- `bash test/bootstrap.test.sh` — 15 проверок, включая красную ветвь «со
  снятой группой тело скрипта теряется»;
- `shellcheck` и `actionlint` чисты; остальные приманки — в описании PR.

Неподтверждённым остаётся всё, что требует самой машины: `ufw`, fail2ban,

действительно закрывает вход. Это различает живой прогон, и его вывод —
доказательство в записи истории, а не в этом файле.

## Последствия

Положительные:

- шаг 2 «Ручных шагов» ADR `2026-10-05-2223` перестаёт ждать рук владельца;
- форма со stdin не оставляет на сервере ни файла, ни следа в истории shell;
- пара REALITY th2 зафиксирована до первой выкатки, значит «профиль
  окончательный» становится свойством выкатки, а не надеждой.

Отрицательные — и честные:

- **Исключение в границе 3 существует.** Оно названо, ограничено предметом и
  числом запусков, но прецедент создан, и следующий «разово» будет легче
  попросить. Противовес один: исключение прописано ADR, который принимает
  владелец, а не решением агента по ходу.
- **Имя `ops` публично.** Защита sshd от этого не меняется, но строка
  «имя пользователя выкатки в репозитории не появится» из ADR
  `2026-10-05-2223` больше не верна.
- **Сбой посередине — консоль провайдера.** Скрипт идемпотентен, но обрыв
  между `ufw --force reset` и `ufw --force enable` оставляет машину без
  файрвола (вход при этом жив). Лекарство — повторный запуск.
- **Пара REALITY th2 лежит на диске Mac владельца** в
  `~/.config/vpn/th2-reality.key`. Это ещё одна копия ключа вне менеджера
  паролей; снятие её после ввода в `put-secrets.sh` — решение владельца, а
  не шаг по умолчанию (без неё ротация потребует новой пары и переимпорта).
- **Перезагрузка th2 отложена** и остаётся за владельцем: контейнеров на
  машине ещё нет, то есть сейчас она бесплатна, а после выкатки стоит
  простоя VPN.

## Альтернативы рассмотрены

- **Запуск владельцем, как в ADR `2026-10-05-2223`** — отклонён владельцем
  («Разово разрешаю агенту»): ожидание его рук на шаге, который не требует
  решений.
- **`scp` + запуск файлом** — оставляет файл на сервере и требует права
  писать туда; выигрыш (защита от съедания stdin) получен формой файла.
- **Закрыть root в том же запуске** — отклонено: ошибка в `authorized_keys`
  оставляет машину без входа, и путь назад только через консоль.
- **Постоянный доступ агента к th2** — не обсуждался и не нужен: после
  bootstrap всё делает `deploy.yml`.
- **Новая пара `x25519` для th2** (как велел ADR `2026-10-05-2223`) —
  отклонена фактом: профиль уже импортирован, и новая пара сделала бы его
  мёртвым при невозможности переимпорта.
- **Имя пользователя выкатки держать в секрете и передавать агенту скрытым
  вводом** — отклонено: агент всё равно пишет его в команду запуска, то есть
  в журнал сессии и в описание PR; изображать секрет хуже, чем назвать цену.

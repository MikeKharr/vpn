# [2026-10-05 16:43] Репозиторий становится приватным: секреты выкатки переезжают на уровень репозитория

Файл: `agent_docs/adr/2026-10-05-1643-private-repo-repository-secrets.md`

## Статус

**Видимость — решение владельца 2026-10-05**, дословно: «move vpn repo to
private»; на вопрос оркестратора «vpn → private: выкатка может потерять
секреты environment на бесплатном тарифе. Как делаем?» — «Сначала PR, потом
private (Recommended)».

Инженерное следствие ниже (снятие `environment: production`, секреты на
уровне репозитория, ветка выкатки в самом файле) — **решение агента роли
platform** в рамках этого решения владельца, отдаётся ему на приёмку вместе
с исполняющим PR класса A. Переключение видимости и завод секретов — руками
владельца; агент на сервер не ходит и секретов не видит (`AGENTS.md`,
границы 2 и 3).

На момент написания: репозиторий публичный, environment `production`
существует и держит три секрета.

Что этот ADR меняет в принятых. ADR
[2026-10-03-0353](2026-10-03-0353-vless-reality-personal-vpn.md):
п. 7 «Публичный репозиторий: что не попадает и что раскрывается» — **посылка
«репозиторий публичный» перестаёт быть верной**, сама граница остаётся
(п. 4 ниже); «Ручные шаги», п. 3 «секреты … в его environment `production`»
— **заменяется**: секреты уровня репозитория. Принятые ADR не редактируются
(I-12 адвента), поэтому в `0353` добавлена одна строка статуса со ссылкой
сюда, а его текст не тронут.

## Почему вообще приходится что-то менять

Secrets уровня environment не работают в приватном репозитории на тарифе
GitHub Free. Источник — документация GitHub, «Managing environments for
deployment», блок требований (дословно):

> Users with GitHub Free plans can only configure environments for public
> repositories. If you convert a repository from public to private, any
> configured protection rules or environment secrets will be **ignored**, and
> you will not be able to configure any environments.

(`github/docs`, `content/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments.md`,
строка 32 на 2026-10-05; на сайте — тот же абзац.) Environment для
приватного репозитория доступен тарифам Pro и Team (там же, строка 34).

**Что было бы, если не менять:** секреты «игнорируются» — то есть
`${{ secrets.SSH_KEY }}` приходит пустым. Выкатка не упала бы молча: шаг
«Секреты выкатки заведены» стоит первым после checkout именно для этого
случая и краснеет с именами отсутствующих значений. То есть цена ошибки —
красная выкатка и живой VPN, а не тихо негодный прод. Но катиться
репозиторий перестал бы.

**Чего эта улика не покрывает.** Тариф аккаунта `MikeKharr` агентом не
проверен: у токена `gh` нет области `user`, и `gh api user --jq .plan`
отдаёт `null`. Free назван владельцем и оркестратором. Если тариф на деле
Pro, environment продолжил бы работать и этот ADR был бы не нужен —
но решение всё равно безвредно: секреты уровня репозитория работают на всех
тарифах и при любой видимости. Разделяющая проверка для владельца — в
«Ручных шагах», п. 0.

## Решение

**1. `environment: production` снимается с job выкатки.** Секреты выкатки
`SSH_KEY`, `SSH_HOST`, `SSH_USER` (и необязательный `SSH_PORT`) живут как
секреты уровня репозитория. `concurrency: deploy-production` остаётся — она
к environment никогда не относилась.

**2. Что environment давал на самом деле — ничего, кроме области видимости
секретов.** Это не рассуждение, а состояние на 2026-10-05
(`gh api repos/MikeKharr/vpn/environments`):

```json
"protection_rules": [], "deployment_branch_policy": null, "can_admins_bypass": true
```

То есть ни обязательных ревьюеров, ни таймера, ни **политики ветвей**.
Защиты, которую нужно было бы «чем-то заменить», не было. Теряется ровно
два: область видимости секрета (был виден только job'у, который называет
`production`; теперь — любому job'у репозитория) и запись в журнале
развёртываний (`/deployments`), которой здесь никто не пользовался.

Расширение области видимости **номинально**: любой workflow этого
репозитория мог сам написать `environment: production` и получить те же
секреты без всякого одобрения — политики ветвей и правил защиты у
environment'а нет, а несуществующий environment workflow создаёт сам
(документация, та же страница, «Running a workflow that references an
environment that does not exist will create an environment with the
referenced name»). Единственный барьер и до, и после — право push в этот
репозиторий.

**3. Ветку выкатки держит шаг в самом файле.** Политика ветвей
environment'а — единственное место, где ветку можно было ограничить
снаружи workflow; её не было, а теперь не будет и места для неё. Поэтому
первым шагом job'а, до checkout, стоит «Выкатка только из main»: он краснеет,
если `github.ref` не `refs/heads/main`.

Это **новая** защита, а не замена: `workflow_dispatch` с произвольной ветки
нёс на прод каталог `deploy` той ветки и до этого PR, и environment этому не
мешал. Признаётся прямо, чтобы запись не читалась как «было — стало».

Почему шаг, а не `if:` на job: пропущенный job красит прогон серой
галочкой, которую легко прочитать как «выкатилось». Последний шаг этого же
файла («Чего выкатка не доказала») существует ровно против такого чтения.

**4. Граница «что не коммитить» остаётся целиком** — список `AGENTS.md`,
п. 1, и `0353`, п. 7, меняется только в обоснованиях:

- приватность **обратима одной командой**, коммит в историю — нет. Секрет,
  попавший в дерево приватного репозитория, становится публичным в тот день,
  когда репозиторий снова откроют;
- сторож `.github/scripts/secrets-guard.sh` и дисциплина «в журнал Actions
  уходят только имена» остаются обязательными и не ослабляются.

**Сознательное отклонение, названное здесь, а не спрятанное:** комментарии,
обосновывающие эту дисциплину словом «публичный», этим PR **не правятся** —
`test/secrets-guard.test.sh:53`, `test/make-clash.test.sh:29,119`,
`bin/make-clash.sh:29`, `bin/make-link.sh:5`, `test/render.test.sh:91`,
`.github/scripts/secrets-guard.sh:2,47`, `.github/workflows/ci.yml:16,146`,
`.github/workflows/deploy.yml:204`. Причина: правило от видимости не
зависит (абзац выше), а сплошная правка десяти файлов в PR про секреты
выкатки смешала бы две задачи. Правятся только **нормативные** утверждения —
`AGENTS.md`, п. 1 и `README.md`, строка 12.

**5. Порядок перехода** (детали — «Ручные шаги»): владелец заводит три
секрета репозитория → мерж этого PR → выкатка проходит **без**
`environment:`, то есть уже только на секретах репозитория → владелец
переводит репозиторий в приватный → повторный прогон выкатки → удаление
environment `production`.

Разделяющая улика здесь — шаг «мерж», а не «удаление environment»: как
только workflow не называет environment, его секреты в job вообще не
подставляются. Зелёная выкатка после мержа доказывает, что работают именно
секреты репозитория. Удаление environment'а после этого — уборка.

**6. Цена приватности в деньгах — минуты Actions.** Для публичных
репозиториев стандартные раннеры бесплатны без лимита; для приватных
расходуется квота плана — **2 000 минут в месяц** на Free, дальше по
тарифу (`github/docs`, `data/reusables/billing/actions-included-quotas.md`;
`content/billing/concepts/product-billing/github-actions.md`, строки 24, 39).
Потолок job'а выкатки — `timeout-minutes: 10`, CI — единицы минут на PR.
Расхождение с этой оценкой в разы (скажем, больше 100 минут в неделю) — повод
разобраться, а не поднять лимит.

## Ручные шаги и проверки

Делает владелец, по порядку. Агент не выполняет ни один из них: это
видимость репозитория, секреты и прод.

**0. Разделяющая проверка тарифа** (одна команда; если ответ `pro` —
останов, этот ADR не нужен, пишите оркестратору):

```zsh
gh auth refresh -h github.com -s read:user && gh api user --jq '.plan.name'
```

**1. Три секрета уровня репозитория.** Значения GitHub не отдаёт — ни
агенту, ни владельцу: прочитать существующий секрет нельзя, его можно
только перезаписать. Поэтому значения берутся у владельца.

Приватный ключ выкатки: **путь к нему в документах не записан нигде** (это
находка этого ADR, а не умолчание). Годится любой приватный ключ, публичная
половина которого лежит в `authorized_keys` пользователя выкатки на сервере.
Найти такой локально:

```zsh
for f in ~/.ssh/*.pub; do ssh-keygen -lf "$f"; done
```

и сличить отпечатки со сервером (ваш обычный вход):

```zsh
ssh <ваш вход на сервер> 'ssh-keygen -lf ~/.ssh/authorized_keys'
```

Совпавший отпечаток — тот ключ. Если ни один не совпал, ключ потерян:
сделайте новую пару и положите публичную половину в `authorized_keys`
своими руками (`AGENTS.md`, граница 2).

Завод секретов. Ключ — файлом, без печати на экран:

```zsh
gh secret set SSH_KEY -R MikeKharr/vpn < ~/.ssh/<файл приватного ключа>
```

Имя сервера и пользователь — скрытым вводом, значение **не** попадает ни в
историю оболочки, ни в список аргументов процесса:

```zsh
printf 'SSH_HOST: '; read -rs v; echo; printf '%s' "$v" | gh secret set SSH_HOST -R MikeKharr/vpn; unset v
printf 'SSH_USER: '; read -rs v; echo; printf '%s' "$v" | gh secret set SSH_USER -R MikeKharr/vpn; unset v
```

`SSH_PORT` — только если порт не 22, тем же видом. Проверка (имена, не
значения; `production` в выводе — это environment, он пока жив):

```zsh
gh secret list -R MikeKharr/vpn
```

**2. Мерж этого PR.** Мерж при консенсусе гейтов делает агент. Мерж сам
запускает выкатку: `deploy.yml` входит в свой же фильтр `paths`. **VPN
рвётся на секунды** — выкатка пересоздаёт оба контейнера (это норма, не
дефект: иначе Xray не перечитал бы конфиг).

**3. Прогон выкатки зелёный.** Это и есть проверка п. 5 решения:

```zsh
gh run watch -R MikeKharr/vpn "$(gh run list -R MikeKharr/vpn -w deploy -L 1 --json databaseId --jq '.[0].databaseId')"
```

Красный шаг «Секреты выкатки заведены» с именами значений означает, что
секрет не заведён или назван иначе — п. 1. Красный шаг про `Permission
denied (publickey)` означает, что в `SSH_KEY` лёг не тот ключ.

**4. Репозиторий в приватный.** Последствия, которые подтверждает флаг:
безвозвратно теряются звёзды и наблюдатели; минуты Actions перестают быть
бесплатными (п. 6 решения); environment `production` и его секреты
игнорируются и настроить environment больше нельзя.

```zsh
gh repo edit MikeKharr/vpn --visibility private --accept-visibility-change-consequences
```

**5. Повторный прогон выкатки — уже в приватном репозитории.** Ровно та
проверка, на которую этот ADR и отвечает. Снова секунды разрыва VPN:

```zsh
gh workflow run deploy -R MikeKharr/vpn --ref main && sleep 5 && gh run watch -R MikeKharr/vpn "$(gh run list -R MikeKharr/vpn -w deploy -L 1 --json databaseId --jq '.[0].databaseId')"
```

**6. Удаление environment `production`** — только после зелёного п. 5.
Удаление сносит и его секреты (документация, та же страница: «Deleting an
environment will delete all secrets and protection rules associated with the
environment»), поэтому шаг последний:

```zsh
gh api -X DELETE repos/MikeKharr/vpn/environments/production
```

**7. Живая проверка** — подключиться с iPhone и Mac. Выкатка этого не
доказывает и доказать не может (`AGENTS.md`, «Проверки»).

## Откат

- **Решение целиком** — откат PR одним коммитом: `environment: production`
  возвращается на job, шаг «Выкатка только из main» снимается. Работает,
  пока репозиторий публичный **и** environment не удалён (п. 6 ручных
  шагов); после удаления environment придётся создать заново и завести в
  нём секреты — руками владельца.
- **Видимость** — `gh repo edit MikeKharr/vpn --visibility public
  --accept-visibility-change-consequences`. Документация обещает, что при
  возврате в публичный прежние правила и секреты environment снова
  доступны. Звёзды и наблюдатели не возвращаются.
- Секреты уровня репозитория после отката можно оставить: workflow,
  который их не называет, их не видит. Снять — `gh secret delete <ИМЯ> -R
  MikeKharr/vpn`.

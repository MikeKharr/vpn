# [2026-10-05 16:00] Xray публикует 443 второго адреса сам, запасной путь — прежний адрес через `sni`

Файл: `agent_docs/development-history/2026-10-05-1600-publish-second-ip.md`

## Что сделано

Исполняющий PR класса A к ADR
[2026-10-05-1546](../adr/2026-10-05-1546-second-ip-xray-direct-happ-back.md),
п. 7 — часть «держатели здесь».

- `deploy/compose.yml`: у службы `xray` появилась **одна** публикация
  `<адрес>:443:8443`. Наружу выходит уже существующий inbound `vless-8443`
  без PROXY protocol — `vless-443` для прямого входа непригоден, потому что
  при `acceptProxyProtocol: true` Xray ставит слушателю политику
  `proxyproto.REQUIRE` (`transport/internet/system_listener.go:170`, v26.9.30
  — проверено по исходнику в ADR, п. 1). `deploy/config.template.json` не
  менялся ни на знак.
- `.github/workflows/ci.yml`: шаг «наружу не публикует ни одного порта»
  переписан в «наружу опубликован ровно один порт» — служба `xray`, форма
  `<конкретный IPv4>:443:8443/tcp`, с положительным контролём формы вывода
  `docker compose config`.
- `.github/workflows/deploy.yml`: после выкатки — живая проверка с раннера
  (`curl --resolve cdn.zpq.ai:443:<адрес из compose>` без `-k` → 200). Шаг
  «Чего выкатка не доказала» поправлен: доходимость снаружи перестала быть
  недоказанной.
- `bin/make-link.sh`: `PORT_FALLBACK=8443` заменён на
  `FALLBACK_ADDR=45.91.134.19`; обе ссылки теперь на порт 443, разница — в
  адресе. Дисциплина скрипта (`read -rs`, печать в терминал, ссылка в
  `qrencode` по stdin) не тронута.
- `README.md`, `AGENTS.md` (граница 4, уточнения в границе 5 и в разделе
  «Проверки»).

## Зачем

Мотив владельца — профилактика: вынести VPN на свой адрес, чтобы «развести
проекты и VPN». Единственный серверный механизм, который сегодня
гарантированно рвёт простаивающее соединение, — `proxy_timeout 10m` у `sni`;
прямой вход этот потолок снимает. Что падения были именно от него, ничем не
подтверждено (журналов у `sni` нет) — это записано в ADR, «Контекст», и
остаётся правдой.

## Порядок

1. Владелец: адрес живёт на хосте (`nc -vz -w 5 <IP> 22` → `succeeded`).
2. PR в `zpq-ai`: `sni` → `45.91.134.19:443:443`.
3. **Только потом** этот PR. Распределитель портов Docker требует, чтобы
   порт на конкретном адресе был свободен и в карте `0.0.0.0` (moby,
   `portallocator.go`, `RequestPortsInRange` — проверено по исходнику в ADR,
   п. 3). При нарушении порядка выкатка падает с `port is already allocated`
   уже после `--force-recreate`, то есть при лежащем VPN.
4. Владелец: A `cdn.zpq.ai` → новый адрес, TTL 300.

## Что ждёт адреса

Нового адреса у владельца на момент PR ещё нет. В `compose.yml` стоит
`203.0.113.1` (RFC 5737, TEST-NET-3) с пометкой «ПЛЕЙСХОЛДЕР» в двух
местах. Пока он там, выкатка краснеет на привязке — мержить PR нельзя.

## Что не проверено

- Живьём ничего: на сервер не ходили, адреса нет. Все проверки — локальные
  тесты, `shellcheck` и прогон CI.
- Красная ветвь нового шага CI прогнана **не локально**: Docker на машине
  автора не запущен, а шаг требует `docker compose config`. Мутации и их
  ожидаемые результаты расписаны в описании PR; различает их прогон CI.
- Что `curl` снаружи вернёт 200, увидит только первая выкатка с настоящим
  адресом.
- Рукопожатие REALITY и подключение устройства — живая проверка владельца
  (ADR, «Ручные шаги», п. 3-5).

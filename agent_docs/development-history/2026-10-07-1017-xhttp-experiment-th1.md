# [2026-10-07 10:17] XHTTP поверх REALITY на запасном входе th1: шаблон, тестовый профиль, держатели

Файл: `agent_docs/development-history/2026-10-07-1017-xhttp-experiment-th1.md`

Шаг 2 ADR [2026-10-07-0920](../adr/2026-10-07-0920-mobile-network-freeze-xhttp-experiment.md),
принятого владельцем. Шаг 1 (пятиминутный тест без PR) дал «все 200», то есть
заморозка на российской мобильной сети — по поведению туннеля, а не по адресу и
не по объёму; варианты «промежуточный сервер в РФ» и «CDN» отпали.

## Что было

Два слушателя в `deploy/config.template.json` говорили одно и то же: VLESS +
Vision по `tcp` поверх REALITY. `vless-8443` — рабочий вход обоих серверов,
`vless-443` — запасной вход **только th1**, достижимый через единицу `sni`
проекта `zpq-ai` по прежнему адресу `45.91.134.19:443` и на th2 не
опубликованный вовсе. На мобильной сети через рабочий профиль проходило ~5 КБ,
дальше соединение замерзало.

## Что сделано

1. **`vless-443` переведён на XHTTP.** `network: "xhttp"`, `xhttpSettings` с
   литеральным `path` (решение владельца, ADR «Решения владельцу», п. 2а),
   `security: reality` без изменений. `flow` у обоих клиентов этого inbound
   снят. PROXY protocol v2 от `sni` переехал из `tcpSettings.acceptProxyProtocol`
   в `sockopt.acceptProxyProtocol`. Рабочий `vless-8443` не изменён ни на знак,
   th2 не тронут.
2. **Параметры набивки выбраны против опасения владельца** «постоянно маленькие
   пакеты тоже подозрительные»: `xPaddingBytes: "100-3000"` — отрезок, а не одно
   число, и сервер набивает им **каждый** ответ случайной длиной. Границы
   выведены из исходника, а не из вкуса — ниже, «Почему именно эти границы».
   `mode: "auto"` на сервере — единственное значение, при котором принимаются все
   три режима клиента.
3. **Отдельный скрипт `bin/make-happ-xhttp-test.sh`** собирает профиль Happ
   «TH mobile TEST»: один outbound XHTTP+REALITY на `45.91.134.19:443` с
   `sni=cdn.zpq.ai`, без балансировщика, без observatory, без `flow`. Ссылка
   приходит скрытым вводом и уходит в python по stdin; в stdout — ровно путь.
   Ключа th2 скрипт не касается, `happ-failover.json` не перезаписывает.
4. **Держатели.** `test/render.test.sh` — проверки «`tcpSettings` у обоих» и
   «Vision у всех клиентов» сужены до `vless-8443` и стали именными, плюс новые:
   `network == xhttp`, `sockopt.acceptProxyProtocol is True`, `tcpSettings` в
   `vless-443` **отсутствует**, ни у одного клиента нет `flow`, `mode == auto`,
   `xPaddingBytes == "100-3000"`. Новый `test/make-happ-xhttp-test.test.sh` —
   сверка профиля полным равенством, права, отсутствие значений в аргументах
   процессов, неприкосновенность соседей по каталогу, `xray run -test`, формы
   отказа. Шаг `ci.yml` «Тестовый профиль XHTTP собирается, и ядро его
   принимает».
5. **README** — раздел «Тестовый профиль XHTTP»: сборка, импорт, как мерить и
   как читать исходы, цена эксперимента, откат через revert. В «Откат» добавлено
   предупреждение: пункт «A-запись обратно без PR» на время эксперимента не
   работает. В шапке и в подсказке `bin/make-link.sh` сказано то же про запасную
   ссылку th1.

## Почему именно эти границы и этот режим — из исходника, не из документации

Читан тег `v26.9.30` — тот же, что у образа в `deploy/compose.yml`.

- **Нижняя граница 100 равна умолчанию ядра**
  (`transport/internet/splithttp/xpadding.go:179-188`), и это не косметика:
  сервер **проверяет** длину набивки клиента на попадание в свой отрезок
  (`hub.go:142-148`). Поднять нижнюю границу значило бы отказывать кодом 400
  клиенту, оставшемуся на умолчании, — а версия ядра в Happ Desktop нигде не
  названа.
- **Верхняя граница 3000 — с запасом под `MaxHeaderBytes` сервера 8192**
  (`hub.go:563`, `config.go` `GetNormalizedServerMaxHeaderBytes`). Набивка
  клиента едет в **заголовке** запроса (`Referer` с `x_padding` у клиента без
  обфускации, `config.go:301-329`), поэтому отрезок до 8000 давал бы 431 вместо
  туннеля.
- **`mode: "auto"` на сервере.** Конкретное значение отказывает клиенту с другим
  режимом кодом 400 — три отдельные ветви: `hub.go:154` (stream-one),
  `:199` (stream-up), `:241` (packet-up). Эксперимент обязан позволить владельцу
  переставить режим в тестовом профиле без PR в серверный шаблон.
- **`stream-up` на клиенте, а не `packet-up`.** `packet-up` гонит наверх
  непрерывный ручеёк мелких POST'ов — ровно тот однообразный рисунок, которого
  опасается владелец. У `stream-up` наверх один длинный POST, вниз один длинный
  GET, и сверх этого сервер досылает в поток набивку случайной длины через
  случайные 20-80 с (`hub.go:219-228`, умолчание `scStreamUpServerSecs`), то
  есть размеры не ложатся в одну величину и в один интервал.
- **`xmux` в профиле не задан намеренно.** Умолчания ядра
  (`infra/conf/transport_method.go:456-462`) держат не больше трёх соединений, а
  «больше трёх параллельных рукопожатий к одному SNI» — сам по себе признак из
  разбора ADR. Своё значение здесь торговало бы один признак на другой.
- **`xPaddingObfsMode` не включён.** При `obfsMode: true` сервер перестаёт
  читать набивку из `Referer` (`xpadding.go:251-268`), то есть клиент с прежним
  ядром получал бы 400 на каждый запрос.
- **PROXY protocol именно в `sockopt`.** Слушатель XHTTP поднимается через
  `internet.ListenSystem(ctx, addr, streamSettings.SocketSettings)`
  (`hub.go:535`), а обёртку `proxyproto` с политикой `REQUIRE` вешает
  `sockopt.AcceptProxyProtocol` (`transport/internet/system_listener.go:169-171`).
  `tcpSettings` при `network: xhttp` не читается вовсе: оставленный там флаг
  тихо перестал бы требовать заголовок, и Xray принял бы `PROXY TCP4 …` за данные
  VLESS.
- **`flow` снят с обеих сторон.** Vision требует «голого» TLS/REALITY —
  `proxy/vless/inbound/inbound.go:581` «XTLS only supports TLS and REALITY
  directly for now»; и обратная сторона: сервер с Vision в аккаунте отказывает
  клиенту без `flow` (`inbound.go:594`, «pure TLS proxy has certain TLS in TLS
  characters»). То есть оставить `flow` на сервере значило бы не подключить
  тестовый профиль вовсе.

## Чего это не доказывает

- **`xray run -test` не ловит оставленный `flow`** и не ловит расхождение
  `path`/`xPaddingBytes` между сервером и клиентом: оба отказа случаются на живом
  рукопожатии и на живом запросе. Поэтому `flow` держит `test/render.test.sh`, а
  согласие транспорта — сверка тестового профиля **с шаблоном**, а не с литералом
  в проверке.
- **Проходит ли XHTTP через `sni` и порог оператора** — это и есть эксперимент.
  Замер с устройства на мобильной сети, README.
- **Совместимость версий ядра** клиента и сервера по XHTTP: у Happ на iOS ядро
  26.9.9, у Happ Desktop версия не названа, на сервере 26.9.30. Проверяется
  только живой пробой.
- **Серверную причину неудачи в журнале не увидеть.** Отказы XHTTP — «invalid
  padding», «… mode is not allowed», несовпадение пути — пишутся через
  `errors.LogInfo`, а `loglevel` у нас `warning` (`AGENTS.md`, граница 7). Это
  находка в бэклоге, не правка этого PR: повышение уровня журнала — решение
  владельца.

## Уроки

- Поле, которое сервер **валидирует**, нельзя выбирать «пошире на всякий случай»:
  у `xPaddingBytes` нижняя граница — это не вкус, а контракт с клиентом, и
  узнать это можно было только в исходнике сервера, а не в документации.
- Перенос флага между секциями `streamSettings` — не косметика: в новой секции он
  работает, в старой тихо игнорируется. Поэтому держатель проверяет **и** наличие
  в новой, **и** отсутствие в старой.
- Два литерала транспорта в двух файлах (шаблон сервера и сборка профиля)
  разошлись бы первой же правкой. Держателем стала сверка одного с другим, а не
  третья копия значения в проверке.

# [2026-10-04 05:13] UDP в туннеле не проходил: причина — реализация TUN в Happ на macOS

Файл: `agent_docs/development-history/2026-10-04-0513-udp-xray-tun.md`

## Симптом

С подключённым Happ на Mac весь UDP через туннель не доходил: `sntp
time.cloudflare.com` (UDP 123) и `dig @1.1.1.1 ... +notcp` (UDP 53) падали по
таймауту. TCP при этом работал. С выключенным Happ в той же сети (хотспот
iPhone) и то, и другое отвечало сразу — то есть дело не в сети и не в
провайдере.

## Как сузили

1. **Базовая линия без VPN** на том же канале: UDP работает. Значит виноват
   путь через туннель.
2. **Выход сервера.** PR #4 добавил в `deploy.yml` пробу только на отчёт:
   прогон выкатки `37177097110` показал, что UDP 53 и UDP 123 проходят и из
   сети хоста, и из docker-сети `edge` — то есть ровно тем путём, которым
   ходит Xray. Серверный выход исключён. PR #5 пробу убрал по решению
   владельца (мерж `eca1fe5`, прогон выкатки `37178249544` — успешен).
3. **Клиент.** Осталась реализация TUN в Happ на macOS, включённая по
   умолчанию.

## Причина и исправление

Happ → Settings → Tunnel Settings → **Xray TUN** включить. Mux остаётся
выключенным: он несовместим с Vision. Отдельной настройки упаковки пакетов в
Happ нет — ядро Xray для Vision использует XUDP само.

## Проверка

После переключения `sntp` и `dig` отвечают, а

```
dig @1.1.1.1 whoami.cloudflare TXT CH +notcp
```

возвращает внешний адрес сервера `45.91.134.19` — то есть UDP действительно
идёт через VPN, а не мимо туннеля.

## Не проверено

iPhone на момент записи не подключён; есть ли на iOS тот же переключатель и
нужен ли он — не проверено.

# [2026-10-06 10:56] Разовый сборщик конфига Happ перенесён в репозиторий

Файл: `agent_docs/development-history/2026-10-06-1056-happ-json-script.md`

PR A-3 по ADR [2026-10-05-2223](../adr/2026-10-05-2223-second-server-triplify-failover.md),
«Ручные шаги», шаг 7.

## Что было

Конфиг Happ с автопереключением th2 → th1 собирал разовый скрипт
`~/Downloads/vpn-happ-failover.sh` на машине владельца. Его выход владелец
импортировал в Happ на Mac (профиль «TH failover»), подключился и проверил
исходящий адрес — `45.91.134.19`, то есть сработавший `fallbackTag` при ещё не
выкаченном th2. Скрипт не был ни в одном репозитории, не проверялся ничем и
не был виден в истории правок.

## Что сделано

- `bin/make-happ-json.sh` — тот же сборщик по правилам репозитория: bash
  вместо zsh (`shellcheck` zsh не разбирает), `umask 077`, скрытый ввод
  ссылки, значения в python только по stdin, в stdout — ровно путь, ключ th2
  не перезаписывается никогда, проверки формы вместо трассировки python.
- `test/make-happ-json.test.sh` — 38 проверок на фиктивных значениях: права
  при рождении и поверх чужих, запрет перезаписи ключа, создание ключа при
  его отсутствии, отсутствие значений в stdout/stderr/аргументах внешних
  команд (PATH из одних обёрток), полное равенство разобранного конфига
  ожидаемому, `xray run -test`.
- Шаг CI «Клиентский конфиг Happ собирается, и ядро его принимает» в job
  `config`.
- `README.md` — раздел «Клиент с автопереключением (Happ, режим JSON)»: импорт
  через буфер, шаг iPhone через Universal Clipboard, различающая проверка
  `ipify`, требование выкатить th2 с существующим ключом и теми же личностями
  устройств.

## Чем доказано, что переимпорта не потребуется

Выход нового скрипта на одних и тех же фиктивных значениях совпал с выходом
разового **байт в байт** (`cmp`, одинаковый md5). Отдельно сверен **уже
импортированный** файл владельца: со скрытыми `id`, `publicKey` и `shortId`
его структура равна структуре выхода нового скрипта, порядок ключей верхнего
уровня тот же, длина обоих файлов 2633 байта. То есть профиль «TH failover» в
Happ — это ровно то, что теперь собирает репозиторий.

## Что осталось владельцу

- Выкатить th2 с ключом из `~/.config/vpn/th2-reality.key` (новая пара
  `xray x25519` отрежет клиента от th2) и теми же UUID/shortId. Значение
  переносится буфером, не печатается: `pbcopy < …`, вставить в скрытое
  приглашение `deploy/put-secrets.sh`, затем `pbcopy < /dev/null`
  (блокирующая `compliance`).
- Четыре расхождения выхода с буквой ADR, п. 4 — из них три поведенческих:
  нет правила `domain:zpq.ai → direct`, нет `enableConcurrency`, **есть**
  лишнее правило `udp 443 → block` (список правил в п. 4 исчерпывающий, и
  лишнее правило — такое же расхождение, как отсутствующее; находка
  `reviewer`). Четвёртое — тег балансера `main` вместо `vpn`, косметика. Всё
  в [`backlog.md`](../backlog.md): исправление любого из трёх стоит
  переимпорта на двух устройствах, а это решение владельца.
- Путь ротации UUID/shortId стал длиннее: после `put-secrets.sh` на обоих
  хостах и выкатки нужен ещё `bash bin/make-happ-json.sh` и переимпорт JSON
  на двух устройствах — переимпорт ссылок профиль «TH failover» не обновляет
  (блокирующая `compliance`; порядок — в `README.md`).
- Снять `~/Downloads/vpn-happ-failover.sh` — команда в `README.md`.

## Что не проверено

Живьём не проверялось ничего из поведения клиента: что `fallbackTag`
срабатывает и за какое время, что сборка Happ на iOS несёт `observatory` и
`balancers`, что импорт через Universal Clipboard доезжает на iPhone. `xray
run -test` разбирает конфиг и не поднимает ни одного соединения. Проверка —
импорт на устройстве (ADR, шаг 7).

# vpn

Личный VPN владельца: VLESS + REALITY на Xray-core. Рабочий вход — порт 443
**второго адреса** сервера, который Xray публикует сам; запасной — прежний
адрес `45.91.134.19` за SNI-маршрутизатором репозитория `zpq-ai`. Клиент —
Happ на Mac и iPhone.

Решение и порядок работ — [ADR 2026-10-03-0353](agent_docs/adr/2026-10-03-0353-vless-reality-personal-vpn.md);
перенос рабочего входа на второй адрес —
[ADR 2026-10-05-1546](agent_docs/adr/2026-10-05-1546-second-ip-xray-direct-happ-back.md).

Серверов будет два:
[ADR 2026-10-05-2223](agent_docs/adr/2026-10-05-2223-second-server-triplify-failover.md)
— `th1` (ReadyIDC, маска `cdn.zpq.ai`) станет резервом, `th2` (Triplify,
`160.236.128.28`, маска `cdn2.zpq.ai`) — основным. Файлы `th2` (наложение,
маска, `bootstrap.sh`) в репозитории уже есть, но **в выкатку он ещё не
включён**: матрица из двух хостов — следующий PR (ADR, «Ручные шаги», п. 6).
Рабочий сервер сегодня — `th1`.

Репозиторий публичный: ключи, UUID, shortId, ссылки `vless://` и QR сюда
не попадают никогда.

## Порядок первой установки

Полный список шагов владельца — ADR, раздел «Ручные шаги и проверки».
Коротко и по порядку:

1. Секреты выкатки `SSH_KEY`, `SSH_HOST`, `SSH_USER` в environment
   `production` этого репозитория; публичный ключ — в `authorized_keys` на
   сервере.
2. В своём терминале: `docker run --rm ghcr.io/xtls/xray-core:26.9.30 x25519`,
   `uuidgen` дважды, `openssl rand -hex 4` дважды. Сохранить в менеджере
   паролей, никуда не вставлять.
3. `SERVER=<пользователь>@<адрес> bash deploy/put-secrets.sh` — пять значений
   уходят на сервер. `SERVER=` обязателен: ключ REALITY у каждого сервера свой.
4. Мерж этого репозитория **первым**: контейнер встаёт в `edge` и снаружи
   недостижим. Порядок не вкусовой — без него выпуск сертификата
   `cdn.zpq.ai` по TLS-ALPN-01 падает (ADR `zpq-ai` 2026-10-03-1544).
5. Мерж PR `zpq-ai` с единицей `sni` — окно простоя 5–20 с на 443 и 80.

Шаги 4–5 — порядок ПЕРВОЙ установки. Для переезда на второй адрес порядок
обратный: сначала PR `zpq-ai`, привязывающий `sni` к прежнему адресу, и
только потом публикация порта здесь — иначе привязка падает с
`port is already allocated` при уже снесённом контейнере. Шаги целиком —
ADR 2026-10-05-1546, «Ручные шаги».
6. Happ по идентификатору `id6504287215`, затем `bash bin/make-link.sh mac th1`
   и `bash bin/make-link.sh iphone th1` (хост — обязательный аргумент).
7. В Happ на Mac и iPhone: Settings → Tunnel Settings → **Xray TUN
   включить**, Mux оставить выключенным (несовместим с Vision). С реализацией TUN по
   умолчанию весь UDP в туннеле не проходит — DNS по UDP 53 и NTP 123
   отваливаются по таймауту при живом TCP (запись истории
   [2026-10-04-0513](agent_docs/development-history/2026-10-04-0513-udp-xray-tun.md)).
8. На Mac DNS сети — публичный резолвер, иначе запросы уходят на роутер
   (частный адрес, он в Direct) мимо туннеля и оператор видит имена сайтов:
   `networksetup -setdnsservers Wi-Fi 1.1.1.1 1.0.0.1`, откат —
   `networksetup -setdnsservers Wi-Fi empty` (нужен для страниц входа
   гостевых сетей). Fake DNS в профиле не включать — с ним имена не
   разрешаются (запись истории
   [2026-10-04-0710](agent_docs/development-history/2026-10-04-0710-dns-leak-mac.md)).
9. Mac с 2026-10-05 — снова Happ, Clash Verge Rev снят: ADR
   [2026-10-05-1546](agent_docs/adr/2026-10-05-1546-second-ip-xray-direct-happ-back.md),
   п. 6. Шаги 7–8 действуют для обоих устройств. Снятие Verge: Tun Mode
   выключить → Settings → Uninstall Service → выйти →
   `brew uninstall --cask clash-verge-rev --zap`. Обход VPN для Яндекс
   Браузера на Happ недоступен — так решено (там же).

   `--zap` ДОЛЖЕН унести и копию профиля, которую Verge держит `0644` со
   значениями (ADR 2026-10-04-1726, «Дополнение 2026-10-05», п. 2), и файл
   прежнего генератора. Что он их унёс — проверить, а не поверить; вывод
   команды различает оба исхода:

   ```sh
   find ~/Library/Application\ Support/io.github.clash-verge-rev.clash-verge-rev \
        ~/Library/Application\ Support/vpn -name '*.yaml' -print 2>/dev/null \
     | grep . && echo 'ФАЙЛЫ СО ЗНАЧЕНИЯМИ НА МЕСТЕ' || echo 'файлов нет — чисто'
   ```

   Если пути напечатаны — в них лежат UUID, `public-key` и `short-id`,
   читаемые любому пользователю машины, и каталоги снимаются руками:

   ```sh
   rm -rf ~/Library/Application\ Support/io.github.clash-verge-rev.clash-verge-rev \
          ~/Library/Application\ Support/vpn
   ```

   Если файл со значениями мог прочитать кто-то ещё (общая машина, бэкап,
   синхронизация каталога) — снять каталог недостаточно, нужна ротация UUID
   и shortId. Полный путь ротации — ниже, в разделе «Клиент с
   автопереключением»: он теперь из четырёх шагов, а не из двух, потому что
   действующий профиль — JSON, и переимпорт ссылок его не обновляет. Это
   решение владельца, а не шаг по умолчанию.

## Клиент с автопереключением (Happ, режим JSON)

Решение — [ADR 2026-10-05-2223](agent_docs/adr/2026-10-05-2223-second-server-triplify-failover.md),
п. 4. Happ отдаёт полный JSON ядру Xray «как есть»: интерфейс Happ в этом
режиме не действует — правила «zpq direct» и Tunnel DNS живут в самом JSON.
Основной сервер — **th2** (`160.236.128.28`, Triplify), резерв — **th1**
(`45.91.134.23`). Переключение делает клиент: `observatory` зондирует th2 раз
в 30 с, и пока он жив — весь трафик через него; когда мёртв — `fallbackTag`
уводит в th1. Когда мёртвы оба — трафик идёт в th1 и не проходит: **ни при
каком исходе он не уходит напрямую**.

### Сборка и импорт

```sh
bash bin/make-happ-json.sh
```

Скрипт спросит рабочую ссылку `vless://` для th1 (ввод не отображается — её
печатает `bash bin/make-link.sh mac th1` — хост обязателен), создаст при
первом запуске пару ключей th2 и напечатает путь к файлу. Дальше — импорт
**через буфер обмена**:

```sh
pbcopy < ~/.config/vpn/happ-failover.json
```

1. **Mac:** Happ → «Импорт из буфера» → профиль «TH failover» → включить.
2. **iPhone:** тот же буфер приезжает Universal Clipboard — на iPhone открыть
   Happ и нажать «Импорт из буфера». Нужны один Apple ID на обоих
   устройствах, включённые Handoff, Bluetooth и Wi-Fi; буфер живёт около
   двух минут. Если не приехал — повторить `pbcopy` и сразу нажать импорт.
3. **Очистить буфер сразу после импорта** — `pbcopy < /dev/null`. В буфере
   лежат UUID, `shortId` и оба публичных ключа: он читаем любым приложением
   Mac, а Universal Clipboard кладёт то же самое в релей Apple и в буфер
   iPhone. Альтернативы у 2,6 КБ JSON нет, но и держать их там после импорта
   незачем.
4. Шаги 7–8 раздела «Порядок первой установки» (Xray TUN, DNS сети) действуют
   и здесь.

### Проверка, и чем она различает исходы

```sh
curl -s https://api.ipify.org; echo
```

- **Пока th2 не выкачен** (его `:443` не отвечает) — `45.91.134.19`. Это не
  ошибка импорта, а сработавший `fallbackTag`: адрес принадлежит th1.
- **После выкатки th2** — `160.236.128.28`, и **переимпортировать ничего не
  нужно**: адрес и публичный ключ th2 уже лежат в импортированном файле.
  Именно в этом смысл JSON — переход на новый сервер не требует рук на
  устройстве.

Других различителей у этой проверки нет: какой сервер выбран, на Mac видно
только по `lsof`, на iPhone — никак (ADR, «Последствия»).

> [!IMPORTANT]
> **th2 ОБЯЗАН быть выкачен с уже существующим ключом и теми же личностями
> устройств.** В импортированном файле стоят: публичный ключ из
> `~/.config/vpn/th2-reality.pub` и UUID со `shortId` того же устройства, что
> на th1. Значит, на th2 уходят через `deploy/put-secrets.sh`:
> `REALITY_PRIVATE_KEY` — ровно из `~/.config/vpn/th2-reality.key` (новая пара
> `xray x25519` сделает th2 недостижимым для клиента), `UUID_*` и `SHORTID_*`
> — те же, что на th1 (ADR, п. 3). Проверить, что ключ на месте и не
> перезаписан, не печатая его:
>
> ```sh
> ls -l ~/.config/vpn/th2-reality.key && wc -c < ~/.config/vpn/th2-reality.key
> ```
>
> 44 байта (43 знака плюс перевод строки) и права `-rw-------` — ключ на
> месте. Повторный запуск `bin/make-happ-json.sh` его не трогает; это держит
> проверка «ключ th2 не перезаписан» в `test/make-happ-json.test.sh`.
>
> **Как положить его на th2, не напечатав.** Приглашение
> `deploy/put-secrets.sh` скрытое, а `cat` ключа оставил бы приватный ключ в
> прокрутке терминала — поэтому значение переносится буфером:
>
> ```sh
> pbcopy < ~/.config/vpn/th2-reality.key
> SERVER=<пользователь>@160.236.128.28 bash deploy/put-secrets.sh
> pbcopy < /dev/null
> ```
>
> В приглашение `PrivateKey` вставить буфер (⌘V — ввод не отображается, это
> так и задумано), остальные четыре значения — те же, что на th1, из
> менеджера паролей. `pbcopy < /dev/null` стоит сразу за вводом, а не
> «потом»: пока ключ в буфере, он читаем любым приложением Mac и, если
> включён Universal Clipboard, уезжает в релей Apple и в буфер iPhone.
>
> **Любая правка этого файла — переимпорт на двух устройствах**, а в поездке
> переимпорт рвёт туннель, то есть требует рабочего VPN, чтобы восстановить
> VPN. Поэтому форма выхода скрипта сверяется в CI полным равенством, а не
> выборкой полей.

### Ротация UUID и shortId: четыре шага, не два

Пока рабочим профилем были ссылки, ротация личности устройства кончалась
переимпортом ссылок. С профилем «TH failover» этого **не хватает**: ссылки и
JSON — разные профили, и обновление одного не обновляет другой. Полный путь:

1. Новые значения на **оба** сервера — `deploy/put-secrets.sh` запускается
   дважды, с `SERVER=` каждого хоста: `UUID_*` и `SHORTID_*` на th1 и th2
   одни и те же, это личность устройства (ADR 2026-10-05-2223, п. 3).
2. Выкатка, пересоздающая Xray на обоих: push в `main` или
   `workflow_dispatch` «deploy». Без пересоздания новые значения не вступают
   в силу — Xray читает конфиг только на старте
   (`deploy/assert-recreated.sh`).
3. `bash bin/make-happ-json.sh` заново и **переимпорт JSON на двух
   устройствах** — через буфер, как при первом импорте.
4. `bash bin/make-link.sh <устройство> <хост>` для каждой пары — только если
   ссылками пользуются как полом; профили th1/th2 в списке тоже держат старый
   UUID. Хост обязателен, и ссылки собираются по разу на хост: публичный ключ
   REALITY у th1 и th2 разный.

Пропустить шаг 3 — значит сделать ротацию, которая выглядит сделанной, а
туннель молча мёртв, и выясняется это в поездке. Держателя у этого порядка в
CI нет и быть не может: все четыре шага — руки владельца на его машине.

Разовый скрипт `~/Downloads/vpn-happ-failover.sh`, которым конфиг собирался
первый раз, **заменён этим файлом** и больше не источник: он не проверяется
ничем и не виден в истории правок. Снять его:

```sh
rm -f ~/Downloads/vpn-happ-failover.sh
```

Выход `bin/make-happ-json.sh` на тех же значениях совпадает с выходом разового
скрипта **байт в байт** — сверено `cmp` до его снятия, поэтому переимпорта
замена не требует.

### Чем выход отличается от буквы ADR

Форма JSON — решение ADR, точные строки — этого PR; **четыре** расхождения
названы прямо, потому что молчаливое расхождение с принятым ADR хуже
названного. Список правил в п. 4 ADR исчерпывающий, поэтому лишнее правило —
такое же расхождение, как отсутствующее:

- тег балансера — `main`, а не `vpn` (ADR, п. 4). Имя внутреннее, на
  поведение не влияет;
- правила `domain:zpq.ai → direct` в конфиге **нет**: трафик к своим сайтам
  идёт через туннель. Петли это не даёт — th2 другая машина, — но лишний
  участок пути есть;
- `observatory.enableConcurrency: true` **нет**: зонды идут последовательно,
  и обнаружение падения медленнее на один таймаут зонда;
- правило `{"network": "udp", "port": "443", "outboundTag": "block"}`
  **есть, а в п. 4 ADR его нет**. Это перенос находки с Mac: через туннель
  UDP/443 не проходил, и Chrome не открывал страницы Google, пока QUIC не
  был отброшен первым правилом (запись истории
  [2026-10-04-1912](agent_docs/development-history/2026-10-04-1912-mac-quic-reject-and-verge-copy-perms.md)).
  Цена названа: QUIC в туннеле недоступен, приложения падают назад на
  TCP/TLS. Блок `dns` и правило `dns-in → balancer` расхождением не
  считаются: ADR оставляет их открытыми прямо («нужен ли `dns`-блок для
  доменных правил — выяснится той же пробой»).

Первое — косметика, остальные три — поведение, и исправление любого из них
стоит переимпорта на двух устройствах. Поэтому они не исправлены здесь, а
отнесены владельцу ([`agent_docs/backlog.md`](agent_docs/backlog.md)).

## Откат

- **Клиент, секунды:** если профиль «TH failover» не подключается — выбрать в
  Happ профиль th1 из `bash bin/make-link.sh <устройство> th1`: он остаётся в
  списке и работает без балансера. Это «пол» ADR 2026-10-05-2223, п. 4;

> [!IMPORTANT]
> **Порядок этих двух PR обратен порядку выкатки, и он обязателен:** сначала
> снять `ports` ЗДЕСЬ, и только потом возвращать `sni` на `"443:443"` в
> `zpq-ai`. Причина — та же карта `0.0.0.0` у распределителя портов Docker,
> что задаёт прямой порядок: пока Xray держит `45.91.134.23:443`, запрос
> `0.0.0.0:443` от `sni` не проходит. А `sni` к этому моменту уже снесён
> `--force-recreate` его выкатки — то есть **лежат все имена машины**, не
> только VPN. Обратный порядок дешевле: снятие `ports` здесь роняет на
> минуты один VPN, у которого на это время остаётся путь через живой `sni`.
